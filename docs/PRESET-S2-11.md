## 1. 프리셋 6종 — 디자인 실물 그대로

`tveEh` / `M0FL0` Equal Layout Preset Grid의 6칸. **정본은 `presets.rs::PRESETS`** 하나다 —
피커도 상태바도 이 목록을 받아 쓴다(하드코딩 금지).

| id | 이름(피커) | 짧은 이름(상태바) | 규칙 | N=8일 때 |
|---|---|---|---|---|
| `grid-2x4` | 2 × 4 그리드 | `2 × 4` | `GRID-COL` | 열 2 · 각 4 |
| `grid-4x2` | 4 × 2 그리드 | `4 × 2` | `GRID-COL` | 열 4 · 각 2 |
| `grid-1x8` | 1 × 8 세로 | `1 × 8` | `GRID-COL` | 한 열에 8 |
| `grid-8x1` | 8 × 1 가로 | `8 × 1` | `GRID-COL` | 여덟 열에 1 |
| `main-right` | 메인 + 우측 스택 | `메인 + 우측` | `MAIN-RIGHT` | 큰 페인 1 + 우측 세로 7 |
| `main-bottom` | 메인 + 하단 나열 | `메인 + 하단` | `MAIN-BOTTOM` | 큰 페인 1 + 하단 가로 7 |

상태바 라벨 `2 × 4 · GRID-COL`은 **`short` + `rule`** 두 칸을 붙인 것이다(`S2-13` 브리프 §1).

**열 우선(`grid-col`) 계승** — 잎은 트리 순서대로 첫 열을 위에서 아래로 채우고, 다 차면 다음 열로
간다(FEATURE-DIFF **H1** · `model.ts:167,223-232`). wmux 문서의 "행 우선"은 틀린 기술이다.

## 2. 결정 셋 — 브리프가 세아 판단으로 남긴 것

### 결정 1. N이 정원과 안 맞을 때 — **열 수를 지키고 행을 늘린다·줄인다**

브리프 §2가 셋 중 하나를 고르라고 했다.

| 후보 | 판단 |
|---|---|
| 빈 칸을 남긴다 | ❌ 트리에 "빈 칸"이 없다. 만들려면 잎을 새로 내야 하는데 **그 잎은 곧 세션이다** — 안 부른 셸이 뜬다 |
| 남는 세션을 마지막 칸에 겹쳐 쌓는다 | ❌ 겹쳐 쌓기는 탭(`S2-5`)이다. 아직 없는 개념을 프리셋이 먼저 발명하면 S2-5가 그걸 물려받아야 한다 |
| **프리셋을 N에 맞춘다** | ✅ 사용자가 클릭한 것은 *"2열로 세로 배치"* 라는 **모양**이다. 그 모양을 지키면서 N을 담는다 |

규칙은 한 줄이다. **열 수 C를 지키고, N을 열에 앞에서부터 고르게 나눈다** (`C_실제 = min(C, N)`).

```
2 × 4 · N=8  → [4, 4]        정원과 같다 — 디자인 그대로
2 × 4 · N=5  → [3, 2]        열은 둘 그대로. 행이 줄었다
2 × 4 · N=11 → [6, 5]        열은 둘 그대로. 행이 늘었다
4 × 2 · N=5  → [2, 1, 1, 1]
8 × 1 · N=3  → [1, 1, 1]     잎보다 많은 열은 못 만든다
메인+우측 · N=5 → [1, 4]      언제나 "하나 + 나머지"
```

**왜 "세로 4개 채우고 새 열"(엄격 계승)이 아닌가.** 그 규칙은 전작에서 *세션이 늘어날 때 자동으로
배치되는* 격자의 규칙이었다. 여기서는 사용자가 `4 × 2`를 **직접 골랐다.** 행을 2로 고정하면 N=5에서
열이 셋이 되어 화면이 `3 × 2`가 된다 — **고른 것과 다른 것이 나온다.**
열 우선은 *채우는 순서*로 계승하고, *열 수*는 사용자가 고른 값을 지킨다.

> **정원(`capacity`) 8은 상한이 아니다.** 디자인이 상정한 세션 수일 뿐이다. N > 8도 거부하지 않는다 —
> 거부하면 사용자는 왜 안 되는지 모른 채 아무 일도 안 일어나는 화면을 본다. 상한은 패널 상한(16)과
> 노드 상한이 이미 든다.

### 결정 2. 프리셋 이름은 언제 떨어지나 — **구조가 바뀌면. 비율은 아니다**

| 사건 | `currentPreset()` |
|---|---|
| `applyPreset(id)` | → 그 이름 |
| **분할·닫기** | → `null` (구조가 바뀌면 이름이 사실이 아니다) |
| **드래그로 비율 변경** | → **그대로 유지** |
| 상태 파일 불러오기 | 이름이 있고 **모양이 맞으면** 유지, 아니면 버린다 |

비율을 유지하는 근거는 디자인 푸터다 — *"적용 후에도 분할선을 드래그해 비율을 조정할 수 있습니다."*
드래그가 이름을 떨어뜨리면 그 문구가 거짓말이 된다.

불러올 때 모양을 대조하는 이유(`presets::still_matches`)는 반대쪽이다 — **틀린 배치 이름이 상태바에
뜨는 것은 이름이 없는 것보다 나쁘다.** 손으로 고친 파일·다른 버전이 쓴 파일이 이름만 남길 수 있다.

> 닫기 뒤 **자동 재배치는 하지 않는다.** 전작 격자는 세션이 줄면 스스로 다시 깔았지만, 그러면
> 사용자가 드래그로 맞춰 둔 비율이 세션 하나 닫을 때마다 날아간다. 이름만 떨어뜨리고 화면은 그대로 둔다.

### 결정 3. 메인 페인 비율 — **3 : 2**

디자인은 "큰 페인 1 + 스택"이라고만 하고 비율을 적지 않았다. `0.6`으로 뒀다 —
8개일 때 나머지 7개가 남은 40%를 나눠도 한 칸이 최소 폭(`MIN_PANEL_PX` 100)을 넘는다.
**출발점이지 결론이 아니다** — 적용 후 드래그로 조정되고, 그래도 프리셋 이름은 유지된다(결정 2).

## 3. 경계 API — `S2-12`(해원) · `S2-13`(이안)은 이 셋만 쓴다

`S2-4` 때 요소 접근자 대신 상태 API(`setZoom`/`zoomedLeaf`)로 답한 그 방식 그대로다.

```ts
import type { PresetInfo } from "./panels";

// 피커 (S2-12) — 목록을 하드코딩하지 말 것. 6종이 늘거나 이름이 바뀌면 여기만 바뀐다.
const presets: PresetInfo[] = await manager.listPresets();
await manager.applyPreset("grid-2x4");

// 상태바·컨텍스트 바 (S2-13) — 동기다. onLayoutChanged마다 불러도 왕복이 없다.
const p = manager.currentPreset();          // PresetInfo | null
setText(layoutEl, p ? `${p.short} · ${p.rule}` : "");
```

| 멤버 | 반환 | 비고 |
|---|---|---|
| `listPresets()` | `Promise<PresetInfo[]>` | 정본이 백엔드라 비동기. 피커 열 때 한 번 부르면 된다 |
| `currentPreset()` | `PresetInfo \| null` | **동기** — 상태바가 매 갱신마다 부르는 값이라 왕복을 안 끼운다 |
| `applyPreset(id)` | `Promise<void>` | 다른 조작과 직렬화된다. 모르는 id는 로그만 남기고 삼킨다(피커가 죽지 않게) |

`PresetInfo`:

| 칸 | 뜻 |
|---|---|
| `id` | 안정 키 (`grid-2x4` …) |
| `label` | 피커 칸 이름 — "2 × 4 그리드" |
| `short` · `rule` | 상태바 라벨의 두 조각 — "2 × 4" · "GRID-COL" |
| `capacity` | 디자인 상정 세션 수(8). **상한이 아니다** |
| `axis` · `groups` | **지금 세션 수 기준** 실제 배치. `axis:"row"`면 `groups`가 열, `"column"`이면 행 |
| `current` | 지금 걸린 배치인가 (`S2-12` — 선택 상태 표시용) |

`groups`가 정원(8) 고정이 아니라 **현재 N 기준**이라, 피커가 *"고르면 이렇게 된다"* 를 그대로
그릴 수 있다(부제 *"현재 팀의 세션 8개"* 의 숫자도 `leafIds().length`로 실물을 쓸 것).

**`layout_apply_preset` 명령을 직접 부르지 말 것.** 트리만 바꾸면 화면(패널 DOM·줌·포커스)이
안 따라온다 — 그 둘을 맞추는 것이 `PanelManager`의 일이다.

> **줌은 프리셋 적용이 이긴다.** 한 패널이 전체 화면을 덮은 상태로 배치를 바꾸면 바뀐 결과를 볼
> 방법이 없다. `applyPreset`이 줌을 먼저 푼다(`focus.ts`가 구조 변경에서 줌을 푸는 것과 같은 판단).

## 4. 🔴 재배열이지 재생성이 아니다 — 무엇으로 보장했나

**보장**: 재배열 경로는 `LayoutState::rearrange` 하나뿐이다. 트리를 해체해 **잎 노드를 그대로 꺼내**
새 모양에 다시 담는다. 잎을 만들지도 버리지도 않으므로 `id`·`pty_id`·`title`·`cwd`가 통째로 옮겨진다.
프런트 `reconcile`은 잎 id로 패널을 캐시하므로 패널 요소도 **위치만 옮겨질 뿐 파괴되지 않는다**
(`panels.ts` 머리말 ③ — 분할 껍데기만 매 렌더 새로 짠다).

**증명**: 화면으로는 구분되지 않는 성질이라(새 셸 8개로 다시 뜬 화면과 옮겨 담은 화면은 똑같이 생겼다)
`--preset-probe`가 신원 넷을 적용 전후로 대조한다.

| 검사 | 무엇을 잡나 |
|---|---|
| `leaves_identical` | 트리가 같은 세션을 **순서까지** 들고 있는가 |
| `ptys_identical` · `pty_per_leaf` | 프로세스가 안 죽었는가 (`pty_list`는 살아 있는 것만 준다) |
| **`canvas_identity_preserved`** | xterm이 파괴·재생성되지 않았는가. **수만 세면 새로 만든 16장도 16장이다** — 요소가 같아야 버퍼·WebGL 컨텍스트가 산 것이다 |
| `renderers_alive` | 재배열 뒤 WebGL 컨텍스트가 살아 있는가 |
| `shape_matches_plan` | 트리가 `listPresets()`가 예고한 배치와 같은가 — **검증은 엔진과 따로 계산한다**(같은 코드로 검사하면 그 코드가 틀렸을 때 통과가 나온다) |
| `current_preset_is_target` | 상태바가 읽을 이름이 실제와 맞는가 |

### 5-3. 8분할 유휴 RAM 참고치 (브리프 §3)

> 🔴 **판정이 아니다.** `#6` 규격은 터미널 **4개**다. 이건 8개로 잰 **비규격 참고치**이고,
> A-4 판정은 해원의 규격 재측정으로만 한다. **숫자만 낸다 — 기준 재검토 여부는 이안 판단이다.**

측정: `tools/perf/s211-idle-ram-panes.ps1` · **핀 exe**(`71ca09b` · sha256 `7509CC03…`) ·
격리 env 3종 · 유휴 정책 켠 채 · `WorkingSet64` · 안정화 30초 후 30초 간격 20표본(10분).

**대상을 핀으로 고른 이유** — 프리셋은 8분할을 *만드는* 기능이지 8분할의 *비용*이 아니다.
그리고 공유 트리에서 갓 빌드한 exe에는 남의 작업 중 코드가 같이 들어 있다(§5-2 경고).

| 값 | **8분할** (M1 · 23:03) | **4분할 대조군** (M1 · 23:16 · 같은 핀) | 차이 |
|---|---|---|---|
| **표본 1~10 중앙값** (`#6` 창과 같은 계산) | **142.2 MB** | **156.6 MB** | **−14.4** |
| 표본 1~20 중앙값 | 157.4 MB | 170.2 MB | −12.8 |
| 표본 20 (~600초) | 159.2 MB | 173.7 MB | −14.5 |
| 범위 | 112.9 ~ 441.2 MB | 123.1 ~ 430.3 MB | |
| 셸 페이로드 (판정 제외) | 761.2 MB | 380.8 MB | +380.4 |

**8분할이 4분할보다 낮다 — 전 구간에서 12~15 MB.** 방향이 예상과 반대라 그대로 적는다.

- 판정선 **219.8 MB** 아래다. **8분할이 기준선을 밀어 올리지 않았다** — 이 측정에서는.
- 그럴 법한 이유: 유휴 RAM은 패널 수보다 **WebView2 상주 바닥이 지배**한다(`SPIKE-A4` — 482 중
  빈 화면 바닥이 380). 창 크기는 같으니 총 픽셀도 같고, 8분할은 패널당 렌더 표면이 절반이다.
  Low가 걷어 가는 것도 그 상주지 패널 개수가 아니다.
- 🔴 **각 n=1이다.** 실행 내 진동은 ±2 MB로 작지만 **실행 간 재현성은 확인하지 않았다.**
  방향을 결론으로 쓰려면 각 3회는 돌려야 한다. **여기서는 방향 신호까지만이다.**
- 유휴 정책은 두 조건 모두 **정확히 한 번** 걸렸다(`유휴 60초 → Low 진입 요청 → Low 적용`).
  진동·재진입 없음 — 8분할에서도 `S2-10` 레버가 그대로 돈다(브리프 §3 마지막 줄).

> 참고로 **M2의 4분할 참고치(S2-10 ④ ≈175.7 MB)와 M1의 4분할 대조군(173.7 MB)이 근접**했다.
> 그렇다고 두 기계를 섞어 쓰지는 않는다 — 이번에 가까웠다는 사실이 다음에도 가깝다는 보장이 아니다.
> **대조군을 실제로 잰 뒤에야 "가깝다"고 말할 수 있었다**는 것이 `#15`의 요지다.

원표본: `tools/perf/s211-idle-ram-panes8.csv` · `s211-idle-ram-panes4.csv`

- 유휴 정책은 **정확히 한 번** 걸렸다 — `유휴 60초 → Low 진입 요청 → Low 적용`. 진동·재진입 없음.
  8분할에서도 `S2-10` 레버가 그대로 돈다(브리프 §3 마지막 줄).
- 셸 페이로드 761.2 MB는 **판정 대상이 아니다**(`#6` — 앱 전용 = eqmux + WebView2). 기록만 한다.

> ⚠️ **S2-10 ④의 4분할 ≈175.7 MB와 직접 비교하지 말 것 — 그 값은 M2, 이 값은 M1이다.**
> `#15`가 못 박은 규칙이 정확히 이것이다(기준선과 대상은 같은 기계에서 잰다).
> 그래서 **같은 기계·같은 핀으로 4분할을 한 번 더 쟀다** — 위 표의 대조군 열이 그것이고,
> **4 → 8의 차이는 그 열끼리만 본다.**

## 6. 교차 검증 — 해원 또는 이안 (`#18` 규칙 2)

**무인 경로 한 줄이면 된다.** 격리 env 3종을 깔고:

```powershell
$exe = "…\src-tauri\target\release\eqmux.exe"
$iso = Join-Path $env:TEMP 'eqmux-preset-x'
$env:EQMUX_STATE_PATH = "$iso\state.json"; $env:EQMUX_WORKSPACE_ROOT = "$iso\ws"; $env:EQMUX_DATA_DIR = "$iso\webview"
& $exe --preset-probe                    # 6종 전수 · 세션 8개 (기본값)
& $exe --preset-probe=main-right --panes=3   # 한 종만 · N 불일치
$LASTEXITCODE                            # 0 통과 · 1 미달. 판정은 stderr 한 줄에도 나온다
```

| 플래그 | 뜻 |
|---|---|
| `--preset-probe` | 6종 전수 확인 후 종료 |
| `--preset-probe=<id>` | 한 종만 |
| `--preset-probe-out=PATH` | 결과 JSON (기본: 상태 폴더 `preset-probe.json`) |
| `--panes=N` | 세션 수. **안 주면 8** |

**손으로 볼 것(무인이 못 보는 것)** — `S2-12` 피커가 붙은 뒤가 더 편하지만 지금도 된다:

1. `--panes=4`로 띄우고 각 패널에 서로 다른 글자를 친다(`echo A`, `echo B`, …).
2. 프리셋을 적용한다(피커 전이면 개발자 도구 콘솔에서 엔진을 직접 부를 수 있다).
3. **각 패널의 스크롤백이 그대로 남아 있어야 한다.** 프롬프트만 새로 있으면 세션이 죽은 것이다.
4. 프리셋 적용 후 분할선을 드래그 → 배치 라벨이 **유지**돼야 한다. 분할·닫기 → 라벨이 **사라져야** 한다.
