# 1부 — 사용성

## U-1 · 페인 헤더에 들어갈 것이 폭의 두 배다

**심각도**: 높음 (0.5 기능 대부분이 이 자리에 기댄다. 넘치면 가장 급한 신호부터 잘린다)

### 워크스루
혼성 4슬롯 팀에서 Codex 개발 세션이 handoff를 받아 30초 넘게 일했다. 그동안 손으로 띄운 에이전트에게 메시지 2건이 쌓였다.
사람이 그 페인 헤더를 본다.

### 기획서대로면 헤더에 오는 것

| 출처 | 요소 | 대략 폭(11px 고정폭) |
|---|---|---|
| §세션 번호 | `03` | 3자 |
| §세션 이름 | `EQMUX03` 또는 `카이` | 8자 |
| §직함 | `클라이언트 개발자` | 한글 9자 ≈ 18자 |
| §직함 · P1 | 직무 배지 `개발`, 엔진 배지 `Codex` | 14자 |
| 지금 | 상태 라벨, 마지막 한 줄 요약(M35), waiting 배지 | 12자 + 남는 폭 |
| §작업 완료 신호 | `✓ 완료` 또는 `✓ 완료 보고`, `보고 없음` + `보고 요청` | 20자 |
| BR-02 | `메시지 2건 · 넣기` | 12자 |

합치면 90자 안팎이다. 2×2 배치에서 페인 폭은 (1440 − 440 − 레일) / 2 ≈ 400px이고, 좌우 패딩 24px을 빼면
11px 고정폭으로 **약 55자**가 들어간다. 8슬롯이면 더 좁다.

### 기획서에 있는 규칙
직함만 "길면 말줄임하고 툴팁으로"(§직함 화면)라고 한다. 나머지는 각 섹션이 따로 "페인 헤더에 칩을 띄운다"고만 적었다.
지금 헤더도 상태·배지가 우선이고 요약이 남는 폭을 쓴다는 규칙만 있다(`ControlCenter.tsx:652`).

### 제안
헤더 우선순위를 한 표로 정해 기획서에 넣는다. 좁아지면 아래부터 빠진다.

1. 행동이 필요한 칩: waiting 배지, `메시지 N건 · 넣기`, `보고 없음`
2. 번호 · 이름
3. 상태 라벨 · 완료 칩
4. 엔진 배지
5. 직함 · 직무 배지 → 넘치면 헤더에서 빼고 툴팁·레일로 보낸다
6. 마지막 한 줄 요약

완료 칩 세 종류는 U-5처럼 하나로 합치면 한 자리가 된다.

## U-2 · 세션 번호가 팀 캐스팅 한 번에 바뀐다

**심각도**: 높음 (수용 기준 "앱을 다시 켜거나 이름을 바꿔도 세션 번호는 바뀌지 않는다"를 지금 코드 그대로는 못 지킨다)

### 워크스루
1. 슬롯 1·2·3에 린·카이·노엘을 둔다. 헤더는 `01 린`, `02 카이`, `03 노엘`이다.
2. 팀 캐스팅에서 카이를 빼고 다시 적용한다.
3. 노엘의 번호를 본다.

### 기획서의 약속
"번호는 슬롯 번호라서 앱을 다시 켜도, 이름을 바꿔도 그대로다."(§세션 번호 표시)

### 지금 코드
캐스팅 적용은 남은 슬롯을 1부터 다시 매기고, 살아 있는 세션의 슬롯을 그 번호로 옮긴다
(`mock.ts:675` `slot: i + 1`, `mock.ts:693` `existing.slot = w.slot`). 노엘은 `02`가 된다.

기본 터미널에서는 더 헷갈린다. 자동 이름은 만들 때 정해져 저장되므로(§사용자 흐름 2), 슬롯 3에서 만든 `EQMUX03`이
슬롯 2로 옮겨지면 헤더가 `02 EQMUX03`이 된다. 자동 이름이 이미 쓰인 경우 "비어 있는 가장 작은 번호"를 쓰는 규칙(§자동 이름 규칙)도
처음부터 번호와 이름이 어긋나는 경우를 만든다.

### 제안
- 캐스팅이 이미 있는 세션의 슬롯을 그대로 두고, 새 페르소나만 빈 슬롯에 넣는다. 번호가 안정돼야 헤더와 레일을 번호로 맞춰 보는 목적이 산다.
- 기획서에서 "자동 이름의 XX = 헤더 번호"라는 약속은 빼고 "만들 때의 번호"라고만 적는다. 둘이 다를 수 있음을 인정하는 편이 덜 놀랍다.
- 수용 기준에 "팀 캐스팅을 다시 적용해도 남은 세션의 번호는 그대로"를 더한다.

## U-3 · 직함 입력 정리가 `C# 개발자`를 `C 개발자`로 만든다

**심각도**: 높음 (사용자가 넣은 값이 말없이 바뀐다. 개발 직무에서 흔한 직함이다)

### 워크스루
역할 라이브러리에서 직함 칸에 `C# 개발자`, `F# 백엔드`, `UI | UX 디자이너`를 넣고 저장한다.

### 기획서대로면
"줄바꿈과 `#`·`|`·`---`는 저장 전에 걷어낸다."(§데이터 모델) 그래서 `C 개발자`, `F 백엔드`, `UI  UX 디자이너`가 저장된다.
"24자 이내로 자른다"도 같은 방식이라 긴 직함은 말없이 끝이 잘린다.

### 제안
- 깨는 자리만 막는다. `#`은 맨 앞에 올 때만 문제다(제목이 되는 것). 제목 줄은 `# 카이 — {직함}`처럼 앞에 다른 글자가 있으니
  가운데 `#`은 무해하다. `|`는 표 안에서 `\|`로 이스케이프한다. `---`는 줄 전체일 때만 문제인데 직함은 한 줄이라 앞에 이름이 붙는다.
- 길이는 입력 칸에 `maxlength=24`와 글자 수를 두어, 자르는 대신 더 못 치게 한다.
- 수용 기준에 "`C# 개발자`가 그대로 저장되고 역할 파일 표가 깨지지 않는다"를 더한다.

## U-4 · "봐야 할 것"을 세는 곳이 넷이 되고 서로 어긋날 수 있다

**심각도**: 중

### 워크스루
waiting 알림이 왔다. 사람은 벨이 아니라 그 페인을 직접 눌러 답했다. 이후 벨을 본다.

### 기획서대로면 미확인 신호
| 신호 | 어디 | 언제 지워지나 |
|---|---|---|
| 세션 `unseen` 점 (waiting·dead) | 헤더·레일 | 페인을 누르거나 점프 (`markSeen`) |
| 세션 `unseenDone` (새로) | 완료 칩 | 같음 |
| 벨 미확인 수 (새로) | 앱 바 | **정하지 않음** |
| 대화 `unread` 점 | 앱 바 대화 버튼 (`AppBar.tsx:47`) | 대화 탭을 읽을 때 |

벨 항목에 읽음 상태가 따로 있으면, 페인에서 이미 처리한 건이 벨에는 계속 미확인으로 남는다.
`다음 미확인으로`의 순서도 둘로 적혀 있다. §주의 고리는 "가장 오래 기다린 순"이고, 대시보드 주의 정렬은 "waiting > dead > 완료·미확인"이다.
완료·미확인이 오래됐으면 waiting보다 먼저 가게 된다.

### 제안
- 벨 미확인 수는 따로 세지 말고 세션의 `unseen`·`unseenDone`에서 계산한다. 페인을 눌러 보면 벨에서도 지워진다.
- `다음 미확인으로`는 대시보드 주의 정렬(waiting > dead > 완료)을 먼저 따르고, 같은 종류 안에서 오래된 순으로 간다.
- 수용 기준에 "페인을 직접 눌러 확인한 건은 벨 미확인 수에서도 빠진다"를 더한다.

## U-5 · 완료 칩이 세 종류이고 `✓ 완료`와 `보고 없음`이 함께 뜬다

**심각도**: 중 ("끝났다"와 "보고가 없다"가 나란히 있으면 끝난 건지 아닌지 읽는 데 멈칫한다)

### 워크스루
기획서의 순서도대로 린이 카이에게 handoff → 카이가 30초 넘게 일하고 턴을 끝낸다. 카이 페인에 `✓ 완료 · 보고 없음`(§작업 완료 신호 순서도)이 뜬다.
이어서 카이가 `report --done`을 보내면 칩이 `✓ 완료 보고`로 바뀐다.

### 제안
칩 하나에 상태 셋을 둔다. 자리를 하나만 쓰므로 U-1에도 도움이 된다.

| 상태 | 칩 | 버튼 |
|---|---|---|
| 턴 완료, 맡은 일 없음 | `✓ 턴 끝남` | — |
| 턴 완료, 열린 handoff 있음 | `✓ 턴 끝남 · 보고 전` | `보고 요청` |
| 완료 보고 | `✓ 완료 보고` (툴팁: 보고 한 줄) | — |

"완료"라는 말은 에이전트가 직접 밝힌 경우에만 쓴다. 앱이 감지한 것은 "턴이 끝났다"까지만 안다.

## U-6 · 워크스페이스를 관리하는 입구가 탭 줄의 "+" 하나만 남는다

**심각도**: 중

### 워크스루
등록한 워크스페이스의 경로가 바뀌어 재지정해야 한다. 또는 안 쓰는 워크스페이스를 등록 해제하려 한다.

### 기획서대로면
앱 바 "워크스페이스" 버튼을 지우고 탭 줄 "+"가 맡는다(§메뉴 정리). 그런데 이 화면은 추가만 하는 곳이 아니다.
열기·`재지정`·`등록 해제`를 모두 여기서 한다(`WorkspaceConnection.tsx:186,234,242`). "+"는 "새로 추가"로 읽혀서,
재지정이나 등록 해제를 찾는 사람은 이 버튼을 누를 생각을 하지 못한다. 지금 "+"의 툴팁도 "워크스페이스 연결"이다(`AppBar.tsx:101`).

### 제안
"+"는 그대로 두고, §바로 가기가 어차피 고치는 워크스페이스 탭 메뉴에 `워크스페이스 관리…` 항목을 하나 더한다.
"+"의 툴팁은 "워크스페이스 열기·관리"로 바꾼다. 두 입구가 같은 화면을 여는 것은 중복이 아니라 자리마다 맞는 이름을 단 것이다.

## U-7 · 대화 탭에 세그먼트가 두 줄로 겹친다

**심각도**: 중

### 기획서대로면
사이드 패널 `대화` 그룹 안에 `[대화 | 로그]` 세그먼트(§메뉴 정리)가 있고, 그 아래 대화 탭 안에 `[이 프로젝트 | 모든 프로젝트]` 전환(§프로젝트 간 통신)이 또 있다.
같은 모양의 컨트롤이 위아래로 붙어 있으면 어느 쪽이 화면을 바꾸고 어느 쪽이 목록을 거르는지 구분하기 어렵다.
440px 폭에서 세로 공간도 두 줄을 쓴다.

### 제안
범위는 세그먼트가 아니라 목록 머리의 필터 칩(`모든 프로젝트 ▾` 또는 토글 칩 하나)으로 둔다.
세그먼트는 "다른 화면으로 바꾸기"에만 쓴다는 규칙을 메뉴 정리에 한 줄로 적는다.

## U-8 · 800자 상한이 사람이 쓰는 메시지에도 걸리는지 정하지 않았다

**심각도**: 중

### 워크스루
사람이 대화 탭에서 리드에게 긴 요구사항을 붙여 넣어 보낸다.

### 기획서대로면
상한 800자와 `--file` 안내는 `eqmux send`(CLI) 기준으로만 적혀 있다(§통신 간소화). 상한은 `messages.rs`에 있으므로
대화 탭 발신도 같은 경로라면 사람의 메시지가 거부되고, 사람은 `--file`이라는 CLI 안내를 받게 된다.

### 제안
둘 중 하나를 정해 기획서에 적는다. (a) 사람 발신은 상한에서 뺀다. 사람이 쓴 글은 사람이 책임진다.
(b) 같이 건다면 입력란에 `n / 800` 글자 수와, 넘으면 "파일로 저장하고 경로를 보낼까요?" 버튼을 둔다. 권장은 (a)다.

## U-9 · "긴 내용은 파일에 쓰라"는데 어디에 쓸지 정하지 않았다

**심각도**: 중

### 워크스루
에이전트가 안내문대로 긴 분석을 파일에 쓰고 `eqmux send --file`로 보낸다. 사람이 git 패널을 연다.

### 기획서대로면
`--file`은 "저장소 안 경로만 받는다". 에이전트마다 `analysis.md`, `notes/kai.md`, `tmp/handoff.txt`처럼 제각각 쓰게 되고,
그 파일들이 git 패널에 추적 안 된 파일로 쌓인다. 사람이 하나씩 지우거나 실수로 커밋하게 된다.

### 제안
역할 파일의 형식 두 줄에 "긴 메시지 파일은 `.eqmux/notes/`에 쓴다"를 더한다. 그 폴더를 커밋할지는 팀이 정하게 두고,
대화 탭에서 첨부를 열 때 그 폴더를 기본으로 보여 준다.

## U-10 · 다른 프로젝트 주소의 `@프로젝트`가 무엇인지 정하지 않았다

**심각도**: 중

### 워크스루
같은 저장소를 두 번 클론해 `app`과 `app`(다른 드라이브)으로 열었다. 또는 워크트리 둘이 같은 폴더 이름을 쓴다.
한쪽 에이전트가 `@카이@app`으로 보낸다.

### 기획서대로면
주소는 `@카이@app-a`처럼 쓴다(§추가할 것 1). `app-a`가 워크스페이스 표시 이름인지 내부 id(`eqmux-1e3b93`)인지는 적혀 있지 않다.
표시 이름이라면 겹칠 수 있고, 자동 이름(`app01`)도 두 클론에서 똑같이 나온다.

### 제안
- 프로젝트 이름이 겹치면 `app`, `app-2`처럼 열린 순서로 접미사를 붙여 주소를 하나로 만든다.
- `eqmux who`와 모호성 오류가 **복사해서 그대로 쓸 수 있는 주소**를 찍는다.
- 수용 기준에 "같은 이름의 프로젝트 두 개를 열어도 주소가 하나로 풀린다"를 더한다.

## U-11 · 이름 개념이 다섯 개다

**심각도**: 낮음

세션 상세 하나에 세션 이름(=표시 이름), 페르소나 이름, 직함, 직무, 그리고 세션 번호가 함께 보인다.
기획서 안에서도 "표시 이름(P5)"과 "세션 이름"을 섞어 쓴다. 화면 문구는 `이름` 하나로 통일하고,
페르소나 이름은 `페르소나`, 직함·직무는 `직함`·`직무`로만 부른다. 기획서도 "세션 이름"으로 통일한다.

## U-12 · 이름 칸을 비우면 무엇으로 돌아가는지가 세션마다 다르다

**심각도**: 낮음

§사용자 흐름 3은 "비우면 자동 이름 규칙으로 돌아간다"고 하고, §결정 7(a)은 역할 세션의 기본을 페르소나 이름으로 둔다.
역할 세션에서 비우면 `카이`로, 기본 터미널에서 비우면 `EQMUX03`으로 돌아간다는 뜻으로 읽힌다. 문장을 그렇게 고치고,
이름 칸의 자리표시자가 비웠을 때 돌아갈 값을 그대로 보여 주게 한다(만들기 다이얼로그와 같은 방식).

## U-13 · `다음 미확인으로`가 단축키에만 있다

**심각도**: 낮음

`Ctrl+Shift+U`(초안)는 써 본 사람만 안다. 단축키 목록 화면은 P2 접근성에 있어 0.5.0에 못 들어갈 수 있다.
벨 목록 머리에 `다음 미확인으로  Ctrl+Shift+U` 버튼을 하나 두면 발견할 길이 생긴다. 이미 쓰는 앱 단축키(`Ctrl+Shift+L`·`D`, `App.tsx:147,164`)와는 겹치지 않는다.

## U-14 · 워크스페이스 탭 메뉴가 길어진다

**심각도**: 낮음

0.5에서 이 메뉴에 음소거(P1), 다른 프로젝트 메시지 받기(§프로젝트 간 통신), 탐색기에서 열기·원격 저장소 열기(§바로 가기)가 들어온다.
U-6을 받으면 `워크스페이스 관리…`까지 다섯 개가 는다. 구분선으로 **열기**(탐색기·원격·관리) / **알림**(음소거·다른 프로젝트 받기) / **닫기**로 묶는다.

## U-15 · 완료 알림 설정 값 `report · all · off`의 화면 문구가 없다

**심각도**: 낮음

설정 키 그대로 보이면 `all`이 무엇을 다 하는지 알 수 없다. 세그먼트 문구를 `완료 보고만`(기본) · `턴 끝날 때마다` · `끔`으로 정해 기획서에 적는다.

## U-16 · 기획서 안의 서로 다른 설명 2건

**심각도**: 낮음 (구현자가 둘 중 하나를 고르게 된다)

- §세션 번호 표시의 예시 `01 기본 터미널`은 "기본 터미널은 항상 자동 이름을 쓴다"와 맞지 않는다. `01 EQMUX01`이 맞다.
- §바로 가기는 파일 트리를 "코드 그룹의 탐색기"라고 하지만, §메뉴 정리의 그림에서 코드 그룹은 `[git | 문서]`뿐이고 탐색기는 임무 팝업 `[임무 | 탐색기]`에 있다(`SidePanel.tsx:3`). "임무 팝업의 탐색기"로 고친다.

# 2부 — 잘 되어 있는 것

- **사람이 마지막에 누른다.** 보고 요청, `검토 중으로`, 손으로 띄운 에이전트에 메시지 넣기(BR-02)가 모두 사람의 클릭에서만 일어난다. 알림 센터도 이동만 한다. 자동으로 뭔가 일어나서 놀랄 일이 없다.
- **전달 결과 응답**(`전달함` / `대기 — 상대 작업 중(대기 N건)` / `실패 — 이유`)은 지금의 "전송됨"보다 훨씬 낫다. 보낸 쪽이 다음 행동을 고를 수 있다.
- **되돌리는 길이 있다.** 직함과 이름은 비우면 돌아가고, `페르소나 직함으로` 버튼이 있다. 버전 업 때 `session.db`를 `.bak`으로 옮긴다.
- **확인창**이 세션 중지·기본 터미널 제거에 들어간다(BR-08, 08-19 평가의 U-3). 앞선 평가의 지적이 해소된다.
- **오류가 다음 행동을 알려 준다.** 800자 초과는 `--file`을, 모호한 이름은 후보 주소를, 상한 무반응은 비활성 + 이유를 보인다.
- **원격 주소에서 토큰을 뗀다.** 화면·툴팁·여는 주소 모두에 적용해, 화면 공유 중에 토큰이 보이는 사고를 막는다.
- **메뉴 정리**가 `PanelTab` 키를 그대로 두어 기존 `openPanel(...)` 호출이 깨지지 않는다. 사람 쪽에서는 탭 7개가 4개로 준다.
- **완료 OS 알림 기본값**(완료 보고만 켬)은 알림 피로를 잘 짚었다. 턴마다 울리면 알림 전체를 끄게 된다는 근거가 맞다.
