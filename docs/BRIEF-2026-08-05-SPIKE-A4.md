# 배정 브리프 — SPIKE-A4 · 유휴 RAM 482 MB 분해

> 배정: 서이안(PM) → **진세아(Dev · 코어 — 관문 성능)** · 2026-08-05
> 배경: **관문 A2 미달** — 482 vs 219.8 MB (2.19배 · [GATE-A2.md](GATE-A2.md) · [RAM-A4.md](RAM-A4.md))
> 성격: **진단 스파이크.** 고치는 작업이 아니다 — **숫자 4개를 만드는 작업**이다. 규모 S~M

## 0. 왜 이걸 하나

482의 95%가 WebView2(458 MB)다. 그런데 **458이 "무엇의 값인지" 아무도 모른다** —
Chromium 상주 바닥인지, WebGL 컨텍스트 4개인지, JS 힙인지. 모르는 채로 내리는 결정은
전부 추측이다. `#19`의 경로(최적화 / 재산정 / 스택 재검토)는 **이 스파이크의 숫자로만** 정한다.

## 1. 만들 숫자 4개

| # | 측정 | 방법 제안 (세아 판단으로 바꿔도 됨) | 답 |
|---|---|---|---|
| 1 | **바닥 B** — 빈 WebView2 | xterm을 로드하지 않는 최소 마크업 모드(플래그 하나) · 격리 · 유휴 60초 | 플랫폼이 깔고 앉는 최소치 |
| 2 | **패널 비용 P** — 1패널 vs 4패널 | `--panes=1`/`--panes=4` 각각 유휴 60초 · (4패널−1패널)/3 | 패널 하나가 먹는 한계 비용 |
| 3 | **프로세스 내역** — 458의 좌표 | msedgewebview2 인스턴스별 `--type=` 인자 + WorkingSet | GPU 프로세스인가 renderer인가 |
| 4 | **플랫폼 레버** — WebView2 공식 감축 수단 | `MemoryUsageTargetLevel(Low)` · 필요시 브라우저 인자. Tauri 2에서 노출되는지 조사 포함 | 공짜로 몇 MB가 빠지나 |

**측정 규격은 판정용(#6)일 필요 없다** — 상대 비교라 유휴 60초 단일값이면 충분하다.
쓰는 김에 해원 하니스(`a2-idle-ram-eqmux.ps1`)를 재활용하면 형식이 맞는다.
**판정용 재측정은 아니다** — 그건 경로 확정 후 해원이 `#6` 규격으로 다시 한다 (검증 분리).

## 2. 미리 박아 둔 판정 기준 ([GATE-A2.md](GATE-A2.md) §3)

- **B + 4P(최적화 후 추정) ≤ 220 근처** → 최적화 경로. 1차 안에서 승부
- **B ≥ ~180 MB** → 219.8은 플랫폼 바닥 아래 → **재산정** ("바닥 + 우리 몫 상한"으로 재유도)
- 스택 재검토는 둘 다 막힐 때만

숫자가 나오면 **세아 씨 의견을 붙여서** 올려 주십시오 — 최적화 여지가 있다고 보는지,
어디가 제일 싸게 빠질 자리인지. 결정은 제가 하지만 **코어 관할의 감각은 세아 씨 것**입니다.

## 3. 조율

- **S2-5(탭)보다 이게 먼저입니다.** `#19`가 S3를 잠갔고, 스파이크가 빠를수록 잠금이 짧습니다.
- S2-3 인수는 별도로 진행합니다 (드래그 육안만 남음 — 제가 봅니다).
- 측정 중 여유 3GB 게이트는 진단용이라 강제 아님 — 다만 **압력을 같이 기록**해 주십시오. 비교니까 조건이 맞아야 합니다.
- 저장소 공유 규칙 그대로 — 경로 지정 커밋.
