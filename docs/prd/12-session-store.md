## 1. 문제 정의

멀티 에이전트 MUX는 8개 세션이 동시에 출력을 쏟아내고, 각 세션은 팀·임무·에이전트 상태를 함께 지닌다.
이 상태를 **누가 소유하고, 언제 디스크에 내리고, 어떻게 되살릴지**가 정해지지 않으면 네 가지가 동시에 무너진다.

- **맥락 소실** — 앱이 죽으면 하루치 에이전트 대화와 출력이 사라진다. 재현 불가능한 작업이 대부분이다.
- **메모리 선형 증가** — 스크롤백을 렌더러 힙에 두면 세션 수에 비례해 램이 늘어난다.
  워크스페이스 10개 × 세션 4개 = **최대 40세션**이므로, 세션당 비용이 그대로 40배가 된다
  (AgentCommender는 10,000줄 × 8페인을 전부 램에 뒀고 그 구간에서 이미 느려졌다).
- **저장 지연 누적** — 상태 파일 전체를 매번 다시 쓰는 방식은 세션·이벤트가 쌓일수록
  디바운스로도 못 막는다.
- **감사 불가** — "어제 이 에이전트가 무슨 명령을 실행했지"에 답할 수단이 없다.
  자동 승인으로 도는 에이전트가 여럿일수록 이 질문의 값이 커진다.

## 2. 목표 / 비목표

### 목표

1. 세션 상태의 **단일 소유 지점**(`SessionService`)을 정의하고 모든 접근을 그 뒤로 몰아넣는다.
2. 스크롤백을 램에서 디스크로 옮겨 **페인 수와 메모리를 분리**한다.
3. 앱 재시작 후 **레이아웃 · 스크롤백 · 에이전트 세션**을 되살린다.
4. GUI 1개 + CLI 다수를 감당하는 **내부 API 경계**를 만든다.
5. 저장소에 **상한과 자동 정리**를 두어 디스크가 조용히 차지 않게 한다.
6. 훗날 별도 프로세스로 분리할 수 있도록 **전송 계층만 교체 가능한 구조**를 남긴다.

### 비목표

- 별도 데몬 프로세스 구현 — C1=② 로 이번 범위 밖
- 원격 · 모바일 클라이언트 구현 — 스키마 대응만 하고 구현은 하지 않음 (C6)
- 에이전트 실행 · 상태 감지 로직 자체 — **PRD D**
- VT 파싱 · 렌더링 — **PRD A**
- 팀 · 임무 도메인 규칙 — **PRD E**
- 사용자 설정 스키마 정의 — **PRD J** (여기서는 저장 매체와 쓰기 방식만 규정)

## 3. 사용자 시나리오

**S1. 재부팅 후 복귀**
워크스페이스 3개에 에이전트를 돌리던 중 노트북을 재부팅한다. 앱을 켜니 워크스페이스 탭과 페인 배치가 그대로이고,
각 페인에 직전 출력 마지막 부분이 그대로 보인다. 재개 가능한 에이전트에는 `재개` 칩이 떠 있고,
누르면 이전 대화에 다시 붙는다. 누르지 않으면 그냥 빈 셸이다.

**S2. 3일 전 실패한 명령 추적**
"지난주에 빌드가 깨졌던 그 명령이 뭐였지." 명령 히스토리에서 exit code ≠ 0 으로 필터하고
해당 명령의 출력 구간으로 바로 이동한다.

**S3. 실수로 창을 닫음**
X를 누르자 확인 다이얼로그가 뜬다. 실행 중인 에이전트 5개가 팀·이름·종류와 함께 나열되고,
그중 2개는 `재개 불가`로 표시된다. 사용자는 그 2개를 먼저 마무리하기로 하고 취소를 누른다.

**S4. 폭주 로그**
한 에이전트가 50만 줄짜리 빌드 로그를 뱉는다. 앱 메모리는 늘지 않고, 위로 스크롤하면
디스크에서 매끄럽게 이어진다. 사용자는 인메모리와 디스크의 경계를 인지하지 못한다.

**S5. 외부 터미널에서 주입**
다른 터미널에서 `eqmux send kai "테스트 다시 돌려"` 를 실행하면 GUI의 해당 페인에 즉시 반영된다.
GUI를 켜둔 채로도 동작한다.

**S6. 한 달 뒤 디스크 점검**
설정에서 저장소 사용량을 본다. 2GB 상한에서 자동 정리되어 있고, 어떤 세션이 얼마를 쓰는지 보인다.

## 4. 기능 요구사항

### 4.1 세션 소유와 수명

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-C-01 | 모든 PTY 세션은 `SessionService`가 단독 소유한다. UI·CLI는 메시지 API로만 접근하며 PTY 핸들에 직접 접근하지 않는다 | P0 |

| FR-C-07 | 세션별 누적 수신 바이트 · 마지막 출력 시각을 기록한다 (대시보드 통계의 원천) | P1 |

## 5. 비기능 요구사항

| 항목 | 목표 | 측정 방법 |
|---|---|---|
| 인메모리 스크롤백 | 활성 세션당 5,000줄 이하 | 힙 스냅샷 |

## 7. 인터페이스

### 7.1 SessionService 메시지

```
요청   create(team, name?, cwd, shell) → SessionId
       close(id, force?)
       write(id, bytes)
       resize(id, cols, rows)
       snapshot(id) → 화면 전체 + 커서
       scrollback(id, from_seq, count) → Line[]
       search(id?, query, range?) → Hit[]
       list(filter?) → SessionMeta[]
       rename(id, name)
       stats(id?) → SessionStat[]    메모리(현재·피크) · 누적 수신 바이트 · 마지막 출력 시각

이벤트 frame(id, bytes)          가시 페인에만, 8~16ms 코얼레싱
       state(id, SessionState)   생성·종료·크래시
       agent(id, AgentSignal)    → PRD D가 정의, C는 전달·저장만

       stat(id, SessionStat)     메모리 샘플 갱신 — 구독 중인 클라이언트에만 (FR-C-09)
```

## 9. 수용 기준

1. 워크스페이스 3개(12세션)에서 각각 `yes`를 동시 실행해 5분간 유지했을 때, 앱 RSS 증가가 예산(§5) 내이고
   활성 탭의 UI가 응답한다. 탭을 전환해도 프레임이 유지된다.
1a. 워크스페이스 10개를 열고 각 4세션을 생성했을 때 앱 RSS가 400MB를 넘지 않는다.
2. 세션당 120,000줄을 출력시킨 뒤, 임의 위치로 스크롤해도 끊김 없이 이어지고 인메모리 상한이 유지된다.
3. 앱을 강제 종료(작업 관리자)한 뒤 재실행하면 레이아웃이 복원되고 각 페인에 직전 500줄이 재생되며,
   에이전트가 있던 세션에 `재개` 액션이 표시된다.
4. `재개`를 누르면 해당 에이전트의 직전 대화에 다시 붙는다. 누르지 않으면 아무것도 실행되지 않는다.
5. 실행 중 에이전트가 있는 상태에서 창을 닫으면, 목록과 재개 가능 여부가 표시된 확인 다이얼로그가 뜬다.
6. GUI를 켜둔 채 CLI 3개를 동시에 접속해 `list` · `send` · `kill`을 실행하면 모두 성공하고
   GUI에 즉시 반영된다.
7. 다른 OS 사용자 계정에서 파이프 접속을 시도하면 거부된다.
8. 상한을 초과하도록 데이터를 채우면 백그라운드 정리가 동작하고, 정리 후 DB 파일 크기가 실제로 줄어든다.
9. DB 파일을 손상시킨 뒤 실행하면 백업 생성 → 재생성 → 사용자 알림 순으로 처리되고,
   설정과 워크스페이스 파일은 온전하다.
10. 웹뷰를 강제 리로드해도 세션이 죽지 않고 화면이 스냅샷으로 복원된다.
11. 세션 상세에 표시되는 메모리 값이 작업 관리자 기준 해당 프로세스 트리 합계와 오차 범위 내로 일치하고,
    40세션에서 샘플링을 켠 상태의 CPU 증가가 0.5% 이하다. 측정이 불가능한 세션은 `측정 불가`로 표시된다.
