## 1. 측정 범위 — 무엇을 `work`로 세는가

```
t0 keydown        t1 파싱 완료                     t2 렌더 완료(onRender)
 │                 │                                │
 ├─[작업 K]────────┤····· 유휴(프레임 대기) ·····├─[작업 R]─┤
 │  xterm 키 처리   │                                │ xterm 렌더
 │  → onData        │                                │ → WebGL draw
 │  → term.write()  │                                │ → onRender
 │    (파서 동기 실행)
 │
 └──────────────────────── total = t2 - t0 ────────────────────────┘
```

| 필드 | 정의 |
|---|---|
| **`work_ms`** | 이 키 입력에 귀속되는 **메인 스레드 실행 시간**. 위 [작업 K]·[작업 R] 구간(그리고 파싱이 비동기로 밀리면 [작업 P])의 **합집합** |
| **`wait_ms`** | `total - work`. 다음 프레임을 기다린 유휴가 대부분이다 |
| `total_ms` | `t2 - t0`. **정의상 항상 `work + wait`** — 두 값이 따로 놀 수 없다 |
| `parse_ms`·`render_ms` | 3점 계측과 같은 정의(`t1-t0` / `t2-t1`). 비교용으로 남겼다 |
| `seg_input`·`seg_parse`·`seg_render`·`frame_wait` | 구간별 내역(진단용) |

**포함**: keydown 핸들러 → 파싱 → 렌더 프레임(`onRender`)
**미포함**: ① OS 키보드 입력 → 브라우저 `keydown` 디스패치 ② GPU가 실제로 픽셀을 내보내는 시각
(프레젠트/스캔아웃). 둘 다 앱 안에서 잴 수 없다.

> **다른 키의 처리 시간은 `work`가 아니라 `wait`에 들어간다.** `work`는 *그 키에 귀속된* 실행
> 시간이다. 같은 프레임에 여러 키가 묶이면(`diag.mean_batch`) 앞선 키의 대기가 길어지는데,
> 그 시간의 성격은 "우리가 일한 시간"이 아니라 "밀린 시간"이므로 대기로 센다.

## 2. 구현 — 왜 이렇게 짰나

### 2-1. rAF 틱으로 자르면 **회귀를 숨긴다** — 데이터로 확인했다

[GATE-A.md](GATE-A.md) §2-1이 경고한 순진한 구현은 이렇다.

```
wait = (t0 이후 첫 프레임 틱) - t0
work = total - wait
```

이 값을 **우리 계측과 나란히 같이 냈다**(`naive_work` 필드). 입력 경로에 5 ms 바쁜 루프를 넣고
같은 표본에서 두 값을 비교한 결과:

| | 무부하 | **5 ms 주입** | 변화 |
|---|---|---|---|
| **`work_ms` p50 (우리 방식)** | 0.2 | **5.1** | **+4.9** ✅ 잡는다 |
| `naive_work` p50 (순진한 방식) | 0.1 | **0.1** | **±0.0** ⛔ **못 잡는다** |
| `naive_work` p99 | 0.3 | 0.2 | −0.1 |

**5 ms를 통째로 넣었는데 순진한 계측은 0.0 ms 변화를 보고한다.** 메인 스레드가 바빠지면
프레임 틱 자체가 밀리므로 늘어난 시간이 전부 `wait`로 흡수되기 때문이다.
경고가 옳았고, 이제 그 경고는 이 저장소의 **측정값**이다.

### 2-2. 그래서 반대로 잰다 — 대기를 재지 않고 **일한 구간을 직접 잰다**

`wait`를 재서 `work`를 빼는 대신, **실행 구간의 시작·끝을 직접 찍고 합집합을 `work`로 삼는다.**
남은 것이 `wait`다. 구간을 놓치면 `work`가 작아지는 게 아니라 `wait`가 커지므로,
**②처럼 없는 부하를 넣으면 반드시 어딘가의 구간이 늘어난다.**

| 경계 | 어떻게 찍는가 | 왜 그 방법인가 |
|---|---|---|
| [K] 시작 = `t0` | **`window`의 capture 단계** keydown | 캡처는 target 단계보다 항상 먼저 돈다 → xterm보다 확실히 앞이다 (§4) |
| [K] 끝 | **`queueMicrotask`** | JS 스택이 완전히 풀린 시각 = 그 태스크의 끝. `onData` 뒤에 xterm이 하는 잔여 작업까지 들어온다 |
| [P] 파싱 | `write` 콜백 + 0 ms 타이머 표식 | xterm은 `_didUserInput`이 서 있으면 **write를 동기로** 파싱한다(`WriteBuffer.write`). 그래서 보통 [P] ⊂ [K]이고, 합집합이므로 이중 계산되지 않는다. 비동기로 밀리는 경로(실측 500회 중 1회)를 위해 표식을 남겨 뒀다 |
| [R] 시작 | **자체 rAF 티커** | 콜백 맨 앞에서 자기 자신을 다시 등록한다 → **항상 그 프레임의 첫 콜백**이라 xterm 렌더보다 먼저 찍힌다. 덤으로 rAF 간격 중앙값 = **실효 주사율**이 나온다(A-3-③ 기록 항목) |
| [R] 끝 = `t2` | `term.onRender` | xterm이 렌더 rAF 안에서 발화한다(`RenderService._renderRows`) |

**LoAF·`longtask`를 안 쓴 이유**: 둘 다 임계값이 50 ms로 고정이라 5 ms 회귀를 못 본다.
**메시지 채널 busy 샘플링을 안 쓴 이유**: 메인 스레드를 계속 돌려 **계측기가 측정 대상을 흔든다.**

### 2-3. 새 플래그

| 플래그 | 뜻 |
|---|---|
| `--latency-probe-inject-ms=N` | **자가 검증 ②** 입력 처리 경로(`onData` 핸들러)에 N ms 바쁜 루프 |
| `--latency-probe-frame-hold=K` | **자가 검증 ③** rAF 콜백을 K프레임마다 한 번만 흘린다 → 유효 주사율 1/K |
| `--latency-probe-gap-ms=N` | 합성 키 간격. 기본 8 |

`--latency-probe-frame-hold`는 콜백을 **모아 뒀다가 나중에 흘릴 뿐 CPU를 태우지 않는다.**
등록 순서를 보존하므로 티커 → xterm 렌더 순서도 그대로다.

## 3. 자가 검증 3항 — 결과 (n=500 · 전부 같은 빌드·같은 기계)

### ① 무부하 기준값

```
--latency-probe-run=500
```

|---|---|---|---|---|---|
| **`work_ms`** | 0.2 | 0.3 | **0.4** | 3.4 | 0.168 |
| `wait_ms` | 8.5 | 16.0 | 16.2 | 16.6 | 8.818 |
| `total_ms` | 8.6 | 16.1 | **16.3** | 16.8 | 8.986 |
| `seg_input` | 0.1 | 0.1 | 0.2 | 1.1 | 0.057 |
| `seg_render` | 0.1 | 0.2 | 0.3 | 2.3 | 0.111 |
| `frame_wait` | 8.5 | 16.0 | 16.2 | 16.6 | 8.825 |

rAF 간격 중앙값 **16.7 ms (59.9 Hz)** · 렌더당 표본 1.88개.
**재현 확인**: 같은 조건 2회차 — `work` p50/p99 = 0.2/0.4, `total` p99 = 16.3 (동일).

> `wait` p50 8.5 ms ≈ **반 프레임**이다. 키가 프레임 중간에 무작위로 도착하니 이론값과 맞는다.
> 총지연의 98%가 프레임 대기라는 뜻이고, 이것이 `#10`이 판정 대상을 바꾼 이유 그 자체다.

| **`work_ms` p99** | 0.4 | **5.3** | **+4.9** | +5.0 ✅ |

### ③ 프레임을 강제로 늦춤 — **`work_ms` 거의 불변, `wait_ms`만 증가**

```
대조군  --latency-probe-run=500 --latency-probe-gap-ms=21
실험군  --latency-probe-run=500 --latency-probe-gap-ms=21 --latency-probe-frame-hold=4
```

| | 대조군 (60 Hz) | **실험군 (유효 15 Hz)** | 변화 |
|---|---|---|---|
| rAF 간격 p50 | 16.7 ms | **66.7 ms** | ×4 (의도대로) |
| **`work_ms` p50** | 0.2 | **0.2** | **±0.0** ✅ |
| **`work_ms` p95** | 0.3 | **0.3** | **±0.0** ✅ |
| **`work_ms` p99** | 0.4 | **0.4** | **±0.0** ✅ |
| `seg_render` p50/p99 | 0.1 / 0.3 | 0.1 / 0.3 | ±0.0 |
| **`wait_ms` p50** | 8.3 | **33.4** | **+25.1** |
| **`wait_ms` p99** | 16.8 | **66.1** | **+49.3** |
| `total_ms` p99 | 16.9 | 66.4 | +49.5 |

**주사율을 1/4로 떨어뜨려도 `work_ms`는 소수점 첫째 자리까지 같다.** 판정값이 주사율에서 분리됐다.

> **이 ③은 "다른 주사율 모니터로 창을 옮긴 것"이 아니다 — 못 한 것을 했다고 적지 않는다.**
> 이 기계는 단일 디스플레이(1920×1080 @ 60 Hz, 최대 100 Hz)라 창을 옮길 다른 화면이 없고,
> 세션 중에 사용자의 디스플레이 모드를 바꾸는 건 화면이 꺼졌다 켜지는 조작이라 하지 않았다.
> 대신 **`GATE-A.md` §2-2가 함께 허용한 "프레임을 강제로 늦춤"** 쪽을 했다. 브라우저는 여전히
> 60 Hz로 프레임을 만들고 우리가 그중 3/4을 건너뛴다 — **앱이 겪는 프레임 간격은 실제로
> 66.7 ms로 측정됐지만**(위 표), 물리적 주사율 변경과 완전히 같지는 않다.
>
> **실패한 시도도 적는다.** `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--disable-gpu-vsync
> --disable-frame-rate-limit`으로 진짜 프레임 생성 주기를 올려 보려 했으나 **rAF 간격이
> 17.2 ms(58.1 Hz)로 그대로였다** — WebView2에서 이 플래그는 먹지 않는다. ③의 근거로 쓰지 않는다.

### ③에서 발견한 함정 — **키 간격을 프레임 주기의 배수로 두면 안 된다**

처음에 `--latency-probe-gap-ms=33`으로 쟀더니 `wait` p50이 **16.7 ms에 고정**되고 분포가
비정상적으로 좁았다(p50 16.7 / p95 17.4). 33 ms는 60 Hz의 **정확히 2프레임**이라 키가 매번
프레임의 같은 위상에 도착한 것이다. 위상이 고정되면 `wait`의 중앙값은 그 위상 하나만 뜻한다.
그래서 ③은 **21 ms**(프레임 주기와 서로소에 가깝다)로 다시 쟀다. 위 표가 그 값이다.
`gap=8`(기준값 ①)은 원래 이 문제가 없다 — `wait` p50 8.5 ≈ 반 프레임으로 이론과 맞는다.

## 4. ⚠️ `S1-3` 계측의 `t0`가 **한 키씩 밀려** 있었다

### 무슨 일이 있었나

옛 코드는 `textarea`에 `capture: true`로 keydown을 걸었다. 그런데 **xterm도 같은 textarea에
keydown을 걸고**(`CoreBrowserTerminal.ts:379`), 이벤트의 target이 바로 그 textarea다.
**DOM 명세상 AT_TARGET 단계에서는 capture 여부와 상관없이 등록 순서로 호출된다.**
xterm이 먼저 등록돼 있으므로 순서는 이렇게 된다.

```
키 i:  [xterm keydown] → onData → t0 = pendingKeydown(= 키 i-1의 시각!) → 비움
                                 → [우리 리스너] pendingKeydown = 키 i의 시각
키 i+1: 같은 일이 반복 → t0는 계속 한 키씩 밀린다
```

즉 **`t0`가 항상 이전 키의 keydown 시각**이었다. 자동 입력 루프가 `sleep(8)`을 쓰므로
모든 표본에 약 8 ms가 얹혔다. `RENDERER-S1-3.md`의 `parse p50 8.8 ms`가 두 기계에서 거의
똑같았던 이유가 이것이다 — **그 값은 파싱 비용이 아니라 루프의 `sleep(8)`이다.**
(xterm은 사용자 입력 직후의 `write`를 **동기로** 파싱한다. 실제 파싱은 `seg_parse` p50 **0.0 ms**다.)

### 숫자로 확인했다 — 추측이 아니다

새 계측기는 옛 경로를 **그대로 같이 재서** 내보낸다(`legacy_total` · `diag.legacy_stale_t0`).

| 실행 | 키 간격 | `total` p50 (고침) | `legacy_total` p50 (옛 방식) | 차이 |
|---|---|---|---|---|
| ① 기준 | 8 ms | 8.6 | 17.5 | **+8.9 ≈ 키 간격** |
| ③ 대조군 | 21 ms | 8.5 | 30.3 | **+21.8 ≈ 키 간격** |

**차이가 키 간격을 그대로 따라간다.** 그리고 `legacy_stale_t0 = 500/500` — **모든 표본**에서
옛 경로의 `t0`가 비어 있거나 새 `t0`보다 과거였다.

### `#10`에 미치는 영향

| | `#10` 인용값 | 이 기계에서 옛 방식 재현 | **고친 계측** |
|---|---|---|---|
| total p99 | 26.1 ms (이안 기계) | **26.0 ms** | **16.3 ms** |

같은 기계에서 옛 방식이 `26.0`을 재현했다 — 원인 규명이 맞다는 뜻이다.

**그래도 `#10`의 결정은 흔들리지 않는다.**

- 고친 값에서도 **총지연의 98%가 프레임 대기**다(`frame_wait` p99 16.2 / `total` p99 16.3).
- 60 Hz에서 한 프레임은 16.7 ms이고 대기만으로 p99가 16.2까지 간다.
  **옛 기준 `p99 ≤ 16 ms`는 정정된 숫자로도 여전히 원리적으로 달성 불가**다.
- 즉 `#10`은 **틀린 숫자를 보고 옳은 판단**을 했다. 판단의 근거였던 구조(프레임 대기가 지배한다)는
  계측을 고친 뒤에 더 선명해졌다.

> **이안에게** — `issue.md` #10과 `RENDERER-S1-3.md` §1·§6-3의 `12.7 / 26.1 / parse p50 8.8` 표기는
> 정정이 필요합니다. 두 문서 모두 제 담당분이 아니라 손대지 않았습니다.
> `12.7 ms`(세아 기계)는 그 기계에서 다시 재야 정정값이 나옵니다 — 그 기계에는 지금 접근할 수 없습니다.

## 9. 한계 — 다음 사람을 위해

1. **`work`는 CPU 시간이 아니라 벽시계 구간이다.** 그 구간에서 OS가 스레드를 뺏으면
   `work`에 포함된다. 5 ms 주입이 4.9 ms로 잡히는 오차(−2%)의 출처도 대부분 여기다.
2. **GPU 시간이 안 들어간다.** `t2`는 `onRender`(메인 스레드가 draw 호출을 끝낸 시각)이고,
   컴포지터가 실제로 화면에 올리는 시각은 그 뒤다. **화면에 보이기까지의 총 시간은 `total`보다 길다.**
3. **③은 시뮬레이션이다** (§3). 물리적 주사율 변경으로 한 번 더 확인할 기회가 있으면 하는 게 좋다.
4. **PTY가 붙으면 다시 재야 한다.** 계측 모드는 로컬 에코다. 지금 값은 렌더 경로의 값이다.
5. **한 프레임에 여러 키가 묶이면**(`diag.mean_batch`) 앞선 키의 `wait`가 길어진다.
   기본 키 간격 8 ms에서 렌더당 1.88개가 묶인다. 사람이 치는 속도(보통 100 ms 이상 간격)보다
   훨씬 빠른 조건이므로, **이 조건의 `wait`는 실사용보다 불리하게 나온다.**

## 10. 인수 판정 (진세아, 2026-08-04)

### 10-0. 결론 — **인수한다.** 갈아엎지 않는다. 단 결함 하나를 고쳤다.

설계가 옳다. `GATE-A.md` §2-1의 함정은 *"대기를 재서 work를 뺀다"* 는 방향 자체에서 나오는데,
이 구현은 **반대로 일한 구간을 직접 재고 나머지를 대기로 본다.** 그러면 구간을 놓쳐도
`work`가 줄지 않고 `wait`가 커진다 — 함정이 구조적으로 안 생긴다. 다시 짜도 같은 설계로 간다.

### 10-1. 자가 검증 3항 — **제가 직접 다시 돌렸다** (남이 낸 표를 옮겨 적지 않는다)

> 그래서 인수 판정에서 이걸 먼저 돌렸다. 통과다.

### 10-2. 🔴 고친 결함 — **자가 검증 실행의 `gate`가 판정처럼 보인다**

인수 전 코드는 ②·③ 실행에도 `gate` 객체를 판정과 똑같은 모양으로 찍었다.

| 실행 | 옛 출력 | 무엇이 문제인가 |
|---|---|---|
| `--latency-probe-inject-ms=5` | `a3_1_pass: true` | **없는 부하를 일부러 5 ms 넣은 값**이다. 5.3 ms라 8 ms 아래여서 "통과"가 찍힌다 |
| `--latency-probe-frame-hold=4` | `a3_2_limit_ms: 133.4` · `a3_2_pass: true` | 유효 주사율을 1/4로 낮췄으니 **2프레임 상한이 33.4 → 133.4로 벌어진다.** 통과가 아니라 무의미다 |

`config`를 같이 읽으면 알 수 있다. 그런데 **`a3_*_pass`만 집어가는 것이 정확히 우리가
문서에 권한 사용법이다** (`README` 계측 절 · 이 문서 §7 — *"gate 객체에 판정이 그대로 들어 있다"*).
집어가는 자리에 표시가 없으면 언젠가 자가 검증 로그가 판정으로 인용된다.

**고침** — `gate`에 두 필드를 넣었다. 계측 경로는 건드리지 않았다.

```json
"gate": { "verdict_valid": false,
          "verdict_invalid_reason": "자가 검증 실행이다 — inject=5ms · frame_hold=1. 판정에 인용하지 않는다",
          "a3_1_work_p99": 5.3, ... }
```

| 실행 | `verdict_valid` |
|---|---|
| ① 무부하 · ③ 대조군 | **`true`** |
| ② `inject=5` · ③ 실험군 `hold=4` | **`false`** + 이유 문자열 |

**재측정이 필요한가 — 아니다.** 요약 JSON에 필드만 추가했고 `work`/`wait`/`total` 산출 경로는
한 줄도 안 바뀌었다. 그래도 고친 뒤 4회를 다시 돌려 §10-1 표와 일치하는지 확인했다. 일치한다.
→ **`GATE-A.md` §4의 A-3 판정은 그대로 선다.**

### 10-3. 인수하며 확인한 것 · 안 고친 것

**확인했고 문제없다고 본 것**

- `renderStart`는 `[t1, t2]`로 잘린다(`latency.ts` `Math.min(Math.max(tick, t1), t2)`).
  프레임 틱을 못 읽으면 **`work`가 작아지는 게 아니라 커진다** — 관문 계측기가 틀리는 방향으로는
  옳다. 통과시키는 쪽으로 안 틀린다.
- `busyLength`가 `[t0, t2]` 밖을 잘라내므로 `work ≤ total`, 따라서 `wait ≥ 0`이 항상 성립한다.
- 프레임 홀드 아래에서도 티커가 xterm 렌더보다 먼저 돈다(콜백 맨 앞에서 자기를 재등록 →
  `pending` 큐의 첫 항목). ③에서 `seg_render`가 0.1로 불변인 것이 그 증거다.

**안 고쳤고 다음으로 넘기는 것**

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **②는 입력 경로만 증명한다** | 주입 지점이 `onData` 안이라 `[작업 K]`만 늘린다. **렌더 경로가 느려졌을 때 잡는지는 증명 안 됐다.** 구조상 `seg_render`가 늘어 `work`에 들어가지만, 그건 논증이지 측정이 아니다. → `--latency-probe-inject-render-ms=N`을 두면 닫힌다. 인수 범위 밖이라 안 넣었다 |
| 2 | 한 배치에 묶인 키들이 **같은 렌더 구간을 각각 `work`로 가져간다** | `mean_batch` 1.88이면 렌더 비용이 두 표본에 각각 계상된다. `work`를 크게 만드는 방향이라 판정에 유리하지 않다. §9-5와 같은 사안 |
| 3 | `installFrameHold`의 `cancelled` 集합이 계속 자란다 | 계측 플래그 없이는 한 줄도 안 도는 경로다. 제품 코드에 영향 없음 |
| 4 | `RENDERER-S1-3.md` · `issue.md` #10의 `12.7 / 26.1 / parse p50 8.8` | 초안 §4가 이미 이안에게 올렸다. **관문·안건 문서라 제가 손대지 않는다** |

### 10-4. 이 인수의 조건

- **A-3 판정 자체는 이안 몫이다** ([GATE-A.md](GATE-A.md) §4). 여기서 한 건 *계측기를 인수한 것*이다.
