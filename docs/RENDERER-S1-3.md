## 1. 키 입력 지연 — A-3

해원이 [BASELINE.md](BASELINE.md) §5에서 요청한 3점 계측을 그대로 넣었다.

```
t0  keydown          → t1  파싱 완료          → t2  렌더 완료
      └── parse ──────────┘ └──── render ────────┘
      └────────────── total ───────────────────────┘
```

### 결과 (n=500)

| 구간 | p50 | p95 | **p99** | max | mean |
|---|---|---|---|---|---|
| **total** | 9.5 | 11.1 | **12.7** | 79.1 | 9.92 |
| parse | 8.8 | 9.9 | 10.6 | 76.1 | 9.02 |
| render | 0.6 | 2.1 | 3.0 | 51.6 | 0.90 |

### 이 숫자를 읽는 법 — 세 가지를 같이 봐야 한다

**① `parse`가 대부분인데, 이건 파싱 비용이 아니다.**
xterm은 `write()`를 큐에 넣고 애니메이션 프레임에서 소화한다. 즉 `parse` 구간은
*"다음 프레임까지 기다린 시간 + 실제 파싱"*이다. 60Hz에서 키가 프레임 중간에 도착하면
평균 8ms를 기다린다. **p50 9.5ms의 대부분은 프레임 대기이고, 이건 결함이 아니라 주사율이다.**
실제 렌더는 0.6ms다 — WebGL 경로는 빠르다.

**② `max`가 큰 것은 워밍업이다.** 첫 표본에서 글리프 아틀라스 생성·JIT가 한 번에 일어난다.
n=50으로 재면 p99가 곧 max라 74ms가 나왔다. **n을 충분히 주지 않으면 p99가 의미 없다.**
관문 A 재측정 때는 최소 500회를 권한다.

**③ 아직 PTY가 없다(S1-2).**
지금 재는 것은 *입력 → 로컬 에코 → 렌더*다. S1-4에서 PTY 왕복이 이 경로에 들어가면
값이 올라간다. **두 시점의 숫자를 섞어 쓰면 안 된다.**

### 측정 범위 — 빠진 구간을 명시한다

| | |
|---|---|
| **포함** | keydown 핸들러 → 파싱 → 렌더 프레임 |
| **미포함** | OS 키보드 입력 → 브라우저 keydown 디스패치 |

앱 밖 구간이라 앱 안에서는 잴 수 없다. `--latency-probe-run`은 합성 `KeyboardEvent`를 쓰므로
이 구간이 빠진다. 결과 JSON의 `note` 필드에도 같은 문장이 들어간다.

> **AgentCommender 쪽 기준선은 여전히 없다.** 같은 계측기를 이식해야 나오고,
> 기능 동결 예외는 이안 판단이다(BASELINE §5-2).
> 다만 **A-3의 통과 판정 자체는 EQMUX 단독으로 가능하다** — "16ms 이하인가"는 위 표로 답이 된다.
> 기준선은 "얼마나 나아졌나"에만 필요하다.

### 재현

```powershell
.\src-tauri\target\release\eqmux.exe --latency-probe-run=500 `
  --latency-probe-out="$env:TEMP\eqmux-latency.jsonl"
```

표본마다 JSONL 한 줄(`parse_ms` / `render_ms` / `total_ms`), 마지막에 요약 한 줄.
요약은 stderr에도 나오므로 파일을 열지 않아도 스크립트가 집어갈 수 있다.

## 2. CJK 폭 — A-2의 절반만 확인됐다

xterm이 배정한 **논리 셀 폭**:

| 문자 | A | 가 | 漢 | ｱ | → | ■ |
|---|---|---|---|---|---|---|
| 칸 | 1 | **2** | **2** | 1 | 1 | 1 |

한글·한자가 2칸으로 잡힌다. `ｱ`(반각 가타카나) 1칸도 맞다.
`→` `■`는 **동아시아 모호폭(ambiguous width)** 문자로, 유니코드 기본값이 1칸이다.
tmux·Windows Terminal도 같다. 필요하면 나중에 옵션으로 뺄 수 있다.

> ⚠️ **이것은 A-2 통과가 아니다.**
> 확인된 것은 xterm이 몇 칸을 **배정하는가**이고, 폰트가 실제로 그 너비로 **그리는가**는
> 눈으로 봐야 한다. 논리 폭이 틀리면 볼 것도 없이 실패이므로 싼 쪽을 먼저 걸렀을 뿐이다.
> **시각 판정은 관문 A에서 해원 몫이다.**

### 폰트 — 이 기계에 한글 코딩 폰트가 없다

현재 스택: `"D2Coding", "Cascadia Mono", "굴림체", "돋움체", Consolas, monospace`

설치된 것을 확인했더니 **D2Coding·Sarasa·NanumGothicCoding 전부 없다.**
Cascadia Mono에는 한글 글리프가 없어 폴백이 일어나고, 폴백 폰트의 advance width가
모노 폭의 정확히 2배가 아니면 **줄이 밀린다.** 굴림체·돋움체는 Windows 기본 제공이면서
ASCII 1칸 : 한글 2칸이 지켜지는 몇 안 되는 폰트라 폴백으로 넣어 뒀다.

**권고: D2Coding을 앱에 동봉하는 것을 검토해 주십시오(이안).**
- 한글 코딩 폰트이고 1:2 비율이 설계상 보장된다
- OFL 라이선스라 동봉 가능하다 (5차 라이선스 확정 때 함께 정리)
- 크기는 약 2~3MB. 현재 배포물이 3.07MB이므로 **두 배가 된다** — 그래서 제 단독 판단으로 넣지 않았다
- 대안: 동봉하지 않고 굴림체 폴백으로 가되, 관문 A에서 시각 판정이 실패하면 그때 넣는다

## 4. 걸린 것 — 다음 사람을 위해

### 4-1. ⚠️ `cargo build --release`는 프런트를 다시 심지 않는다

**여기서 제일 오래 막혔다.**

프런트 번들은 `tauri::generate_context!`가 **컴파일 시점에** 실행 파일 안으로 심는다.
그런데 `dist/`만 바뀌고 Rust 소스가 그대로면 cargo는 다시 빌드할 이유가 없다고 본다.
결과: **빌드는 성공하는데 옛 프런트가 박힌 바이너리가 그대로 남는다.**

증상이 고약하다 — 고친 코드가 실행되지 않는데 오류도 없다.
CSP를 의심해 껐다 켜고, stdout/stderr를 바꾸고, 로그 경로를 새로 만들면서 한참을 헤맸다.

> **`cargo tauri build`를 쓴다.** `npm run build`를 먼저 돌리고 이 관계를 처리한다.
> 굳이 cargo를 직접 부를 일이 있으면 `cargo clean -p eqmux --release`를 먼저 한다.
> README 빌드 절에도 적어 뒀다.

### 4-2. GUI 서브시스템에서는 `println!`이 사라진다

`#![windows_subsystem = "windows"]`이면 stdout 핸들이 붙지 않는다.
**로그는 전부 `eprintln!`(stderr)로 낸다.** 여기서 한 번 로그를 통째로 잃었다.

### 4-3. 프런트 예외가 아무 데도 안 남았다

웹뷰 콘솔은 창을 열고 F12를 눌러야 보인다. 무인 실행에서 프런트가 죽으면 흔적이 없다.
`src/log.ts`를 만들어 `window.onerror` · `unhandledrejection` · 명시적 로그를
전부 `log_front` 명령으로 프로세스 stderr에 끌어냈다. **이게 없으면 눈이 먼다.**

### 4-4. 화면 캡처로 검증하지 않는다

렌더러 확인을 스크린샷으로 하려다 **창이 포그라운드로 올라오지 않아 팀장님 화면이 찍혔다.**
이미지는 즉시 삭제했다.
지금은 전부 파일·stderr 산출물로 검증한다 — 무인이고, 재현되고, 남의 화면을 안 건드린다.
`report_renderer`가 그 자리를 담당한다.
