## #1 팀 기본 임무는 잠금인가 아닌가

**상태**: 결정 대기 · **종류**: 설계 · **관련 단계**: 4차 (페르소나 팀모드)

### 배경

AgentCommender 문서 두 개가 **정반대 동작**을 명세한다. 어느 쪽이 코드인지 문서로는 알 수 없다.

| 문서 | 주장 |
| --- | --- |
| `Tech.md:145` · `Tech.md:294` | **잠금이다** — 담당 프로젝트를 지정하면 그 팀 세션은 다른 임무에 배정할 수 없고, 기존 배정은 확인 후 일괄 해제되며, 이후 배정은 경고와 함께 차단된다 |
| `Mission_Spec.md:94` | **잠금이 아니다** — "담당은 잠금이 아니다". 기본값일 뿐이고 세션별로 다른 임무를 배정할 수 있으며, 다른 임무를 맡은 세션은 건드리지 않는다 |
| `Feature_Map.md:167` · `Tech_check_List.md:66` | 잠금 아님 쪽 (3:1) |

### 정해야 할 것

EQMUX 4차에서 **팀 기본 임무를 어느 쪽으로 승계할 것인가.**

- **A. 잠금** — 팀 단위 집중 규율. 한 팀이 여러 임무에 흩어지는 걸 구조적으로 막는다.
- **B. 기본값** — 유연. 팀장이 팀원마다 다른 임무를 줄 수 있다.

의견: **B**. 실제로 지금 Administrator 팀은 셋 다 EQMUX 하나를 보지만, 4차의 "팀 편성"은
역할이 갈리는 걸 전제한다(리뷰어가 다른 저장소를 볼 수 있어야 한다). 다만 이건 제 의견이고
**결정은 이안·팀장님 몫**이다.

### 영향 범위

EQMUX 4차 임무 모델 · 영속 스키마(`teamProjects`) · 관제 UI 경고 유무

의견: **간다.** AgentCommender가 이미 마이그레이션 비용을 치른 문제를 다시 밟을 이유가 없다.
`WORKPLAN.md:110`의 **S3-4 스키마 버전 필드**와 함께 처음부터 넣는 게 맞다.

## #3 "배정 = 착수"의 전달 방식 분기

**상태**: 결정 대기 · **종류**: 설계 · **관련 단계**: 4차

### 배경

임무를 배정할 때 세션에 무엇을 보내는가.

| 문서 | 동작 |
| --- | --- |
| `Tech.md:144` · `Tech.md:293` | 무조건 `cd "<임무 경로>"` 전송 |
| `Mission_Spec.md:78~92` | **세션이 무엇을 돌리는지에 따라 갈린다** — 셸이면 `cd`, 에이전트 실행 중이면 자연어 브리프 |

`Mission_Spec.md:87`이 굵게 경고한다:

> **"에이전트 프롬프트에 `cd`를 치면 폴더가 아니라 대화가 바뀔 뿐이다."**
> 이 구분이 없으면 Claude Code를 띄운 세션에서는 배정이 아무 일도 하지 않는 것처럼 보인다.

즉 `Tech.md`가 기술하는 동작은 **Mission_Spec이 명시적으로 경고한 함정 그 자체**다.

### 정해야 할 것

두 가지가 걸려 있다.

1. **분기를 승계하는가** — 승계가 맞아 보인다. 이건 확인만 받으면 된다.
2. **무엇으로 판별하는가** — 여기가 진짜 안건이다.
   - AgentCommender는 `SessionInfo.agent` **선언값**을 쓴다(우클릭 '에이전트 실행'으로 띄웠을 때만 기록).
   - 사용자가 세션에서 에이전트를 직접 껐다 켜면 **선언과 실측이 어긋난다.**
   - `Mission_Spec.md:92`가 자인하고 로드맵 FS-6(프로세스 실측)으로 대체 예정이라고 적혀 있다.

의견: EQMUX는 **처음부터 실측으로 간다.** Rust 백엔드가 PTY의 pid를 소유하므로 프로세스 트리를
내려가 자손을 확인하는 비용이 낮다. 선언값을 먼저 만들면 나중에 두 소스가 공존한다.

### 영향 범위

4차 임무 배정 · 세션 상태 판정 · (연동) 관문 A 이후의 에이전트 상태 감지

## #6 관문 A-4 유휴 RAM 판정 기준

**상태**: 결정 대기 · **급함** · **종류**: 설계 · **관련 단계**: 관문 A

### 배경

`WORKPLAN.md:77` 관문 A-4: **"유휴 RAM — 기준선(S0-1) 대비 40% 이하"**
브리프의 S0-1 정의: **"터미널 4개 띄우고 10분 방치 후 전 프로세스 WorkingSet 합"** = 프로세스 트리 전체

S0-1 실측(`BASELINE.md` §3):

| 구성 | RAM | EQMUX에서 사라지나 |
| --- | --- | --- |
| electron (앱) | 566.3 MB | **사라진다** |
| pwsh · conhost · 기타 (셸 페이로드) | **454.0 MB** | **안 사라진다** |
| 트리 전체 | 1,020.3 MB | |

```
트리 기준 목표 = 1,020.3 × 0.4 = 408.1 MB
EQMUX에도 남는 셸 페이로드   = 454.0 MB

454.0 > 408.1  →  EQMUX 앱이 0 MB여도 미통과
```

**앱을 아예 안 만들어도 실패하는 기준이다.** EQMUX도 같은 `pwsh`를 띄우고 ConPTY는 `conhost`를 붙인다.

### 정해야 할 것

- **A. 앱 전용 RAM으로 판정** (제안) — 기준선 566.3 MB → 목표 **226.5 MB**.
  트리 값은 계속 기록하되 판정에는 안 쓴다.
- **B. 트리 유지하되 목표율 완화** — 예: 70%. 하지만 셸 페이로드가 바닥이라 비율이 실제 개선량을 안 나타낸다.
- **C. 셸을 제외한 트리** — 앱 + 앱이 만든 부속(conhost 등), pwsh만 제외. 경계가 애매하다.

의견: **A.** 재작성이 개선할 수 없는 부분을 판정에 넣으면 안 된다.

### 영향 범위

관문 A 판정 · `PRD-EQMUX.md` 성능 목표 · `OBJECTIVES.md:133` 지표

## #7 앱 데이터(브라우저 캐시) 상한 시점

**상태**: 열림 · **종류**: 설계 · **관련 단계**: 1차 (`S3-6`) 또는 그 이전

### 배경

S0-1 실측(`BASELINE.md` §6):

| | 앱 데이터 | 캐시 계열 비중 |
| --- | --- | --- |
| wmux | 497.6 MB | **95.6%** (Code Cache 281.7 + Cache 194.1 + …) |
| AgentCommender | 46.5 MB | 같은 구성 (Cache 20.3 + Code Cache 8.3 + …) |

**wmux의 512MB는 wmux의 결함이 아니라 Chromium 캐시가 상한 없이 자란 결과다.**
AgentCommender도 같은 메커니즘을 갖고 있고 덜 자랐을 뿐이다.

> **Tauri/WebView2로 가도 이 문제는 안 사라진다. WebView2는 Chromium이다.**
> Tauri가 없애는 건 *배포물에 실린 런타임 347MB*이지 *실행 중 쌓이는 캐시*가 아니다.

### 정해야 할 것

`WORKPLAN.md:112`의 **`S3-6`(스크롤백 + 디스크 상한 강제)이 S3에 있다.**
관문 B는 **2주 도그푸딩**이고, 캐시는 그 2주 동안에도 자란다.

- **A. 그대로 S3** — 도그푸딩 중 캐시가 자라도 2주면 크지 않을 것이라 보고 진행.
- **B. S1/S2로 앞당김** — WebView2 데이터 폴더 상한·주기적 정리를 골격 단계에 넣는다.
  `OBJECTIVES.md:130` R10 *"상한은 코드에 박는다"*의 취지에 더 맞다.
- **C. 측정 후 결정** — 도그푸딩 1주 시점에 캐시 크기를 재고 그때 판단.

의견: **B 또는 C.** 최소한 **도그푸딩 시작 시점에 캐시 크기를 재는 절차**는 넣어야 한다.
안 재면 "EQMUX가 가볍다"를 배포 크기로만 말하게 되고, 그건 사용자가 체감하는 용량이 아니다.

### 영향 범위

`S3-6` · 관문 B 절차 · `OBJECTIVES.md:133` 지표(배포물 ≤40MB에 앱 데이터가 포함되는지 불명확)
