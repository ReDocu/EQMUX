### 격리 방식 — 라이브 인스턴스를 건드리지 않았다

측정 시점에 AgentCommender가 **팀 4개(Administrator·WordDoc·NovelTeam·EduCraft) · 세션 10개**를 물고
실행 중이었다. 이 문서를 쓰는 세션도 그 안에 있다(`pwsh ← claude.exe ← pwsh ← electron.exe`).

**앱을 재시작하면 살아 있는 세션이 전부 죽으므로, 별도 인스턴스를 띄워 측정했다.**

```
--user-data-dir=<임시>          Electron 단일 인스턴스 락 회피 (락은 userData 경로 기준)
ACMUX_STATE_PATH=<임시>/state.json    라이브 state.json 미접촉
ACMUX_WORKSPACE_ROOT=<임시>/ws        라이브 워크스페이스 미접촉
```

→ 라이브 인스턴스(PID 24388)와 상태·워크스페이스·userData가 완전히 분리된 채로 측정됐다.
측정 후 격리 인스턴스와 그 자손 프로세스를 전부 종료했다.

> **이 방법은 EQMUX에도 그대로 필요하다.** 도그푸딩(관문 B) 중에는 EQMUX도 팀 세션을 물고 있을 것이므로,
> 재측정 때 같은 격리 스위치가 없으면 측정 자체가 파괴적 행위가 된다. **S1 단계에서 세아에게 요청한다.**

### ⚠️ 격리로도 분리되지 않는 것 — 명명 파이프 (이안 지적, 2026-08-04)

`ACMUX_STATE_PATH`·`ACMUX_WORKSPACE_ROOT`·`--user-data-dir`은 상태·워크스페이스·캐시를 분리하지만
**제어 파이프는 분리하지 못한다.** 코드 실측:

| 근거 | 내용 |
| --- | --- |
| `main/control-server.ts:6-9` | `pipePath()`가 `'\\\\.\\pipe\\acmux'`를 **하드코딩**한다. 환경변수 오버라이드 없음 |
| `cli/acmux.ts:9-10` | CLI도 같은 값을 하드코딩 |
| `control-server.ts:37-40` | `listen()` 실패 시 `console.error` 한 줄만 찍고 **재시도·크래시 없이 넘어간다** |

**실제 동작**: Windows 명명 파이프는 첫 생성자가 이름을 점유한다(libuv는 `FILE_FLAG_FIRST_PIPE_INSTANCE` 사용).
두 번째 인스턴스의 `listen`은 `EADDRINUSE`로 실패하고, 위 핸들러가 그것을 **조용히 삼킨다.**

> **따라서 나중에 뜬 인스턴스는 파이프를 빼앗지 못하고, 제어 서버 없이 뜬다.**
> `acmux send`는 계속 **먼저 뜬 쪽(=라이브)** 으로 간다 — 오배송은 일어나지 않는다.
> 실측 확인: 격리 측정 후 `acmux list`가 라이브 세션 10개를 정상 반환했다.

**그래서 위험은 반대 방향에 있다.**

| 순서 | 결과 |
| --- | --- |
| 라이브 먼저 → 격리 나중 | 안전. 격리 쪽 제어 서버만 죽는다 (측정에는 무관) |
| **격리 먼저 → 라이브 나중** | **위험.** 격리가 파이프를 쥐고, 라이브의 제어 서버가 조용히 죽는다 |

**규칙 (측정 시 반드시 지킬 것)**

1. 격리 인스턴스는 **라이브가 이미 떠 있을 때만** 띄운다.
2. **격리 인스턴스가 떠 있는 동안 라이브를 재시작하지 않는다.**
3. 측정 전후로 `acmux list`를 찍어 라이브 세션이 나오는지 확인한다.
4. 격리 인스턴스를 쓰기 전에 **이안에게 먼저 알린다.**

**EQMUX 설계 요구 (→ 세아)**: 제어 채널 이름을 **환경변수로 덮어쓸 수 있게** 만들 것
(`EQMUX_PIPE_NAME` 등). 3줄이면 되고, 이게 없으면 EQMUX도 같은 제약을 물려받아
도그푸딩 중 측정이 불가능해진다. AgentCommender 쪽은 기능 동결이라 **측정 한정 예외**로만 판단.

## 2. 콜드 스타트 — 1,531 ms

### 정의

> **T0** = 앱 프로세스 생성 시각 (`Get-Process.StartTime`, 커널 기록값)
> **T1** = 첫 세션의 `session.log`에 첫 바이트가 기록된 시각 = **셸 프롬프트가 그려진 시점**

### 결과

| 구간 | 1회차 (15:47) | 2회차 (17:11) | 차이 |
| --- | --- | --- | --- |
| T0 → T1 (첫 프롬프트) | 1,531 ms | **2,127 ms** | +596 ms (+39%) |
| T0 → 터미널 4개 전부 준비 | 3,186 ms | **2,184 ms** | **−1,002 ms (−31%)** |

> ### ⚠️ 두 표본이 반대 방향으로 움직인다 — 아직 값을 확정하면 안 된다
>
> 1회차는 첫 프롬프트(1,531) 뒤 나머지 3개가 뜨는 데 **1,655 ms**를 더 썼고,
> 2회차는 첫 프롬프트(2,127) 뒤 **57 ms** 만에 4개가 다 떴다. **곡선의 모양 자체가 다르다.**
>
> 추정(미확정): 1회차는 디스크 캐시가 차가워 첫 셸이 빨리 뜨고 나머지가 지연됐고,
> 2회차는 캐시가 더워 4개가 거의 동시에 떴다. PTY 스폰 순서·타이밍이 실행마다 달라진다.
>
> **n=2로는 어느 쪽도 대표값이 아니다. 관문 A 판정 전에 n=10 중앙값·p95가 필요하다.**
> 지금 이 두 값은 **자릿수 감각(1~3초대)** 으로만 쓸 것.

- 세션 4개를 미리 담은 `state.json`을 복원시키는 조건이다(사용자가 앱을 켜면 마주하는 실제 상황).
- 팀 모드는 `terminal` — 규약 파일 스캐폴드가 없어 파일 I/O가 최소인 조건이다. **가장 유리한 값**이다.
  `persona` 모드는 `ROLE.md`·`CLAUDE.md`·`Persona/` 스캐폴드가 붙으므로 더 느리다(미측정).

### 이 값의 한계 — 반드시 같이 읽을 것

1. **"입력 가능"이 아니라 "프롬프트 출력"이다.** 브리프의 정의는 *"첫 프롬프트 입력 가능까지"*인데,
   외부에서 "입력을 받을 준비가 됐다"를 관측할 방법이 없다. 프롬프트 출력은 그 직전이며 **하한값**이다.
2. **pwsh 프로필 로딩이 포함돼 있다.** 셸 자체의 기동 시간이 섞여 있다. EQMUX도 같은 셸을 쓰므로
   **비교에는 문제없지만**, "앱이 1.5초를 쓴다"로 읽으면 안 된다.
3. **1회 측정이다.** 분산을 모른다. 관문 A 재측정 때는 10회 반복 후 중앙값·p95를 쓴다.

### 재현 절차

```powershell
# 1) 격리 환경 준비
$env:ACMUX_STATE_PATH     = "<임시>/state.json"   # 팀1 × 세션4, mode=terminal 로 시드
$env:ACMUX_WORKSPACE_ROOT = "<임시>/ws"
# 2) 기동
$p  = Start-Process <electron.exe> -ArgumentList '<ops>','--user-data-dir="<임시>/udata"' -PassThru
$t0 = (Get-Process -Id $p.Id).StartTime
# 3) 20ms 폴링으로 <ws>/BASE/t1/session.log 의 Length > 0 시각 포착 → T1
# 4) 콜드스타트 = T1 - T0
```

**EQMUX 측정 시**: EQMUX가 세션 로그를 안 쓴다면 등가 신호를 하나 정해야 한다
(권장: PTY의 첫 출력 바이트를 받은 시각을 앱이 stderr/로그로 1줄 찍게 하는 측정 전용 플래그).
**신호를 바꾸면 두 숫자는 비교 불가다.**

### ⚠️ 먼저 — §2는 `M3`에서 잰 값이다

§1이 적은 측정 환경은 `Windows 11 Home 10.0.22631`인데 **M1은 `Windows 11 Pro 10.0.26200`이다.**
오늘 업그레이드된 것이 아니라는 근거는 [MACHINE-SPEC.md](MACHINE-SPEC.md) §1에 있다.
**§2의 1,531 / 2,127 ms와 아래 값을 같은 표에 올리면 안 된다.**

### 방법을 두 군데 고쳤다 — §2의 하니스에 결함이 있었다

| # | 무엇이 틀렸나 | 고친 것 |
|---|---|---|
| **1** | **T1 정의.** §2는 *"session.log 첫 바이트 = 셸 프롬프트가 그려진 시점"* 이라고 했다. **아니다.** `pty-manager.ts:111-112`가 세션 **생성 즉시** `──── 세션 시작 … ────` 헤더를 쓴다. 첫 바이트는 **셸 출력이 아니라 앱이 쓴 헤더**다 | 두 값을 **분리해서** 잰다 — `세션생성`(헤더) / `첫프롬프트`(헤더 줄 **뒤에** 처음 붙은 실내용) |
| **2** | **폴링이 파일을 독점 모드로 열었다.** `[IO.File]::ReadAllText`는 앱이 쥔 파일에서 **공유 위반으로 100% 실패**한다. 조용히 false를 돌려주므로 **영원히 감지되지 않는다** | `FileShare.ReadWrite \| Delete`로 연다. 이걸 고치자 719 ms 안에 프롬프트까지 다 보였다 |

> **1번이 §2 값의 해석을 바꾼다.** §2의 `1,531 ms`가 헤더(=세션 생성)를 잡은 것이라면
> 그건 **프롬프트 시각이 아니라 그 이전**이다. §2를 폐기하진 않되 **"프롬프트까지"로 읽지 말 것.**

### 이 값의 한계 — **"콜드"가 아니다**

10회를 **3.3초 간격으로 연속 기동**했다. 디스크 캐시가 전부 뜨겁다.
분산이 작은 것(448~506, 폭 58 ms = 12%)은 **앱이 안정적이어서가 아니라 조건이 균일해서**다.

> **그런데 이게 §2의 미해결 질문에 답을 준다.**
> §2는 두 표본이 39% 벌어진 원인을 *"디스크 캐시 온도"* 로 **추정(미확정)** 했다.
> 캐시를 통제하니 분산이 12%로 줄었다 — **그 추정을 지지하는 간접 증거다.**
>
> **진짜 콜드(부팅 직후 최초 실행) 값은 여전히 없다.** 재부팅당 1표본밖에 못 얻고
> 대기 목록 비우기는 관리자 도구가 필요하다. 필요하면 지시 주십시오.

### EQMUX와 비교할 때

### 3.1 ⚠️ 관문 A-4 — "구조적 불가능"에서 "여유 27.3 MB"로 정정

> **정정 (2026-08-04 17:25).** 이 절의 이전 판에서 A-4가 *구조적으로 통과 불가능*하다고 적었다.
> 그 계산은 **95초 표본**(트리 1,020.3 / 셸 454.0)에 근거한 것으로, **10분 규격값이 아니었다.**
> 규격값으로 다시 계산하면 **산술적으로는 통과 가능하다.** 아래가 정정된 계산이다.

WORKPLAN 관문 A-4: **"유휴 RAM — 기준선(S0-1) 대비 40% 이하"**
브리프 S0-1 정의: **"터미널 4개 · 10분 방치 · 전 프로세스 WorkingSet 합"** = **트리 기준**

```
목표치 = 985.5 MB × 0.4 = 394.2 MB
EQMUX에도 그대로 남는 셸 페이로드(pwsh 338.5 + conhost 28.4) = 366.9 MB

394.2 - 366.9 = 27.3 MB   ←  EQMUX 앱 전체에 허용된 몫
```

**즉 EQMUX의 앱 프로세스(Tauri 호스트 + WebView2 프로세스군) 전부가 27.3 MB 이하여야 한다.**

### 27.3 MB가 현실적인가 — 참고값

이 머신에서 도는 WebView2 프로세스군 실측(다른 앱 소유, **EQMUX 실측이 아닌 참고값**):

| 인스턴스군 | 프로세스 | RAM |
| --- | --- | --- |
| A | 6개 | **142.2 MB** |
| B | 6개 | **80.0 MB** |
| C (거의 유휴/축소 상태) | 6개 | 11.0 MB |

Tauri 앱은 Rust 호스트 + WebView2 프로세스군으로 구성된다. **WebView2만으로 27.3 MB를 넘을 가능성이 높다.**
C군이 11 MB인 걸 보면 극단적으로 축소된 상태는 가능하지만, xterm.js + WebGL을 4개 띄운 상태가
거기에 들어갈 것으로 기대하기는 어렵다.

> **결론이 "불가능"에서 "매우 빠듯함"으로 바뀌었을 뿐, 권고는 같다.**
> 그리고 이 27.3 MB라는 값 자체가 **86 MB 진동 폭보다 작다** — 측정 노이즈가 목표치의 3배다.
> 진동 구간 최저점(552.5) 기준으로 재면 트리 919.1 × 0.4 = 367.6, 셸 366.9 → **여유 0.7 MB.**
> **표본을 언제 뜨느냐로 통과 여부가 갈리는 기준은 판정 기준으로 못 쓴다.**

**제안 — A-4를 앱 전용 RAM으로 재정의**

| | 현재 (트리) | 제안 (앱 전용) |
| --- | --- | --- |
| 기준선 | 985.5 MB | **618.6 MB** (600초 표본) / 552.5 MB (중앙값) |
| 40% 목표 | 394.2 MB → **실질 여유 27.3 MB** | **247.4 MB** (중앙값 기준 221.0 MB) |
| 측정 대상 | 자손 프로세스 전부 | EQMUX 호스트 + WebView2 프로세스군만 |
| 노이즈 대비 | 여유(27.3) < 진동폭(86.5) ❌ | 목표(247.4) > 진동폭(86.5) ✅ |

트리 값도 계속 기록하되 **판정은 앱 전용으로** 한다. 재작성이 개선할 수 없는 부분을 판정에 넣으면 안 된다.

> 이건 제 제안이고 **판정은 이안 몫**입니다. `issue.md #6`에 최종 숫자를 넣었습니다.

### 3.2 ~~관찰 — 유휴 상태인데 프로세스를 계속 스폰한다~~ → **재현 실패, 철회**

> **정정.** 95초 측정(v2)에서 `conhost` 5→6→9개, `tasklist` 1→1→5개가 관측되어
> *"관제 대시보드가 5초마다 netstat/tasklist를 스폰한다"* 고 적었다.
> **10분 측정(v3)의 11개 표본에서는 `tasklist` 0개 · `netstat` 0개 · `conhost` 4개(pwsh 1개당 1개)로 고정이었다.**
> **한 번도 재현되지 않았다.**

| | v2 (95초) | v3 (600초 · 11표본) |
| --- | --- | --- |
| conhost | 5 → 6 → 9 | **4 고정** |
| tasklist | 1 → 1 → 5 | **0** |
| netstat | (미계측) | **0** |
| 총 proc | 14 → 16 → 22 | **12 고정** |

가능한 설명 두 가지 — **어느 쪽인지 확정 못 했다:**

1. 포트 폴링은 실제로 돌지만 수명이 짧아(수백 ms) v3의 표본 11개가 전부 빗나갔다.
   (5초 주기 × 200ms 수명 = 듀티 4%. 11회 전부 놓칠 확률 ≈ 64% — **가능하다**)
2. v2 측정 당시 다른 조건(패널 상태 등)이 폴링을 유발했다.

**따라서 "유휴 앱이 5초마다 프로세스를 스폰한다"는 주장은 철회한다.**
확인은 `S0-2`에서 `main/ports.ts` 호출 지점을 읽어 판정한다. 코드를 보면 1분이면 끝난다.

**EQMUX 설계 메모는 유효하다** — 폴링을 하든 안 하든, Rust는 프로세스 스폰 없이 조회할 수 있다
(`netstat` 대신 IP Helper API, `tasklist` 대신 프로세스 열거). 그대로 이식하지 않는 게 좋다.

## 5. ⛔ 키 입력 지연 — 이 방법으로는 측정 불가

**측정하지 못했습니다. 추정치를 적지 않겠습니다.**

### 왜 막혔나

관문 A-3의 기준은 **p99 ≤ 16 ms**다. 16ms는 60Hz 기준 **한 프레임**이다.

- 외부(PowerShell·CLI)에서 재면 프로세스 기동 오버헤드가 수십~수백 ms라 **측정 대상보다 잡음이 크다.**
- `acmux send` → `session.log` 왕복으로 재면 **xterm 렌더링 구간이 통째로 빠진다.** 그 구간이 바로
  WebGL이 걸린 자리이고, S1-3의 관심사다. 빼고 재면 의미가 없다.
- 고속 카메라·하드웨어 계측은 이 환경에 없다.

### 해제 조건 — 앱 안에 계측기가 있어야 한다

키 입력 지연은 **두 앱 모두에 같은 계측기가 들어가야** 비교가 성립한다.

```
keydown 이벤트 타임스탬프 (performance.now)
   → xterm term.write() 직후
   → 렌더 완료 콜백 (WebGL 프레임 present / requestAnimationFrame)
= 이 구간을 앱이 직접 기록해 p50/p95/p99로 뱉는다
```

**요청 (→ 세아 · 이안 판단)**

1. **측정 전용 플래그**를 EQMUX S1 단계에 넣어 주십시오 — `--latency-probe` 같은 스위치로
   위 3점을 JSONL로 뱉게. **S1-3(WebGL 동작 확인)의 판정 근거가 바로 이 숫자입니다.**
2. AgentCommender 쪽 기준선은 **같은 계측기를 이식**해야 나옵니다.
   기능 동결 중이므로 **측정 코드 한정 예외**가 필요합니다 — 이안 판단 부탁드립니다.
3. 그 전까지 **관문 A-3은 판정 불가**입니다. 기준선이 없으면 "16ms 이하"는 통과 여부를 말할 수 있어도
   "AgentCommender보다 나아졌나"는 말할 수 없습니다.

> 대안이 하나 있습니다 — 개발자도구(F12)를 열어 렌더러에 계측 스니펫을 붙이는 방식.
> GUI 조작이 필요해 제가 단독으로 못 합니다. **필요하면 지시해 주십시오.**

## 6. ❌ 브리프 수치 정정 — "앱 데이터 ~0 MB"

브리프 §1과 `OBJECTIVES.md:37`의 표:

| | AgentCommender | wmux 0.13.0 |
| --- | --- | --- |
| 앱 데이터 | ~0 MB | 512 MB |

**대조군이 어긋나 있습니다.**

| 실제로 잰 것 | 경로 | 크기 |
| --- | --- | --- |
| 브리프의 "~0 MB" | `~\AgentCommender\` (state.json 하나) | 0.003 MB |
| **같은 성격의 대조군** | `%APPDATA%\agent-commender\` (Electron userData) | **46.5 MB** |
| wmux | `%APPDATA%\wmux\` | **497.6 MB** |

`~\AgentCommender\`는 우리가 만든 상태 파일 폴더이고, wmux의 512MB는 **Electron userData 전체**다.
같은 층을 비교하면 **46.5 MB vs 497.6 MB**다.

### 그래서 결론이 바뀌나 — 부분적으로 바뀝니다

**우위는 유지된다** (10.7배). 하지만 **원인 해석이 달라진다.**

wmux 497.6 MB의 구성:

| 항목 | 크기 | 비중 |
| --- | --- | --- |
| Code Cache | 281.7 MB | 56.6% |
| Cache | 194.1 MB | 39.0% |
| Dictionaries | 10.9 MB | 2.2% |
| GPUCache | 5.6 MB | 1.1% |
| **캐시 계열 합** | **475.8 MB** | **95.6%** |

AgentCommender 46.5 MB도 구성이 같다 — Cache 20.3 · Code Cache 8.3 · Dictionaries 10.9 · GPUCache 5.6.

> **wmux의 512MB는 wmux의 결함이 아니라 Chromium 캐시가 상한 없이 자란 결과다.**
> AgentCommender는 같은 메커니즘을 갖고 있고, 단지 **덜 자랐을 뿐이다**(설치가 더 최근, 브라우저 패널 사용이 적음).

### EQMUX에 주는 함의 — 이게 제일 중요합니다

**Tauri/WebView2로 가도 이 문제는 안 사라집니다. WebView2는 Chromium입니다.**

- Tauri 전환이 **안** 없애는 것: **실행 중 쌓이는 브라우저 캐시**
