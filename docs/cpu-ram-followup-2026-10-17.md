# CPU·RAM 후속 점검 — 0.5.1 기준 (2026-10-17)

같은 날 나온 `cpu-optimization-2026-10-17.md`·`cpu-ram-risks-2026-10-17.md`의 후속이다. 그 두 문서에서 남은 항목을 코드로 다시 확인했고, 두 문서가 보지 않은 자리를 더 찾았다. 앱이 꺼져 있어서 앱 실측은 하지 않았다. CLI 실행 비용만 직접 쟀다.

## 요약

- **CPU는 이미 측정 하한에 있다.** 앞 문서의 릴리스 실측을 보면 유휴 상태는 본체·렌더러 모두 0.00%다. 실사용(터미널 8개)에서도 본체가 약 0.04코어, 렌더러가 약 0.03코어를 쓴다. CPU를 더 깎아도 체감할 만한 이득은 없다.
- **0.5.2 후보로 적어 둔 CPU 후속 4건 중 3건은 할 필요가 없다.** 코드를 확인해 보니 이미 해결돼 있거나 비용이 없었다(아래 §1).
- **남은 지렛대는 RAM이다.** 실사용 때 전체 메모리는 렌더러 95~120MB, GPU 120~152MB, 본체 30MB 정도다. 싸게 시험해 볼 만한 것은 세 가지다(아래 §2). 하나는 최소화했을 때 WebView2에 "메모리를 적게 써라"를 알리는 것이고, 나머지는 숨긴 브라우저 패널과 스크롤백 상한이다.

## 1. 앞 문서 후보 중 하지 않아도 되는 것

| 후보 | 확인한 것 | 판단 |
|---|---|---|
| 커서 깜빡임을 포커스된 페인만 (`TerminalPane.tsx:579`) | xterm이 이미 그렇게 한다. WebGL 렌더러의 `CursorBlinkStateManager`는 `handleBlur`에서 `pause()`, `handleFocus`에서 `resume()`을 부른다. 깜빡임 타이머는 `isFocused`일 때만 다시 건다(`@xterm/addon-webgl` 번들) | **안 한다.** 지금도 포커스된 터미널 하나만 깜빡인다 |
| UnicodeGraphemesAddon 끄기 (`TerminalPane.tsx:592`) | `charProperties`에 ASCII 빠른 길이 있다(`e>=32&&e<127` → 미리 만든 값을 그대로 돌려준다). 비ASCII(박스 문자·한글)만 트라이 표를 한 번 찾는다. 이 애드온을 빼면 이모지 폭이 어긋나 Ink 표가 깨진다(그 주석이 이유다) | **안 한다.** 비용은 작은데 빼면 화면이 깨진다 |

| `[profile.dev.package."*"] opt-level = 2` | 개발 빌드에서만 효과가 있다 | 원하면 한 줄. 릴리스에는 영향이 없다 |

### 새로 확인한 것 — 문제 없음

- **훅·상태 줄 CLI 실행 비용.** `eqmux _hook`·`_statusline`은 14.5MB짜리 GUI exe를 그대로 띄운다. 그래서 작은 CLI를 따로 빼야 하는지 쟀다. 20회 평균 결과는 이렇다.

  | 실행 | 벽시계 | CPU |
  |---|---|---|
  | `cmd.exe /c exit` | 22~25ms | 9~11ms |
  | `eqmux.exe --version` | 24ms | 16~23ms |

  cmd.exe 한 번 띄우는 것보다 CPU 5~12ms가 더 든다. 도구 호출 한 번에 훅 2번(Pre·Post)이 돌므로, 바쁜 에이전트 4명이면 초당 수십 ms 수준이다. 별도 바이너리로 나누면 빌드·배포 경로가 둘이 되는데, 그만한 값이 없다. **안 한다.**
  - 참고로 앱이 꺼져 있으면 `_hook` 한 번에 약 330ms가 걸린다. `ipc::request`가 100ms씩 쉬며 3번 재시도하기 때문이다. 앱 없이 에이전트를 돌릴 때만 해당하고, 에이전트를 막지는 않는다(훅 timeout 5초).
- **전역 tick 구독 40곳.** `listSessions()`·`listMessages()`는 배열을 복사하지 않고 원본을 그대로 돌려준다. 메시지는 300건 상한이 있고(M3), 방송은 16ms로 묶인다(후보 1). 남은 구독은 세션 수십 개를 훑는 정도다.
- **번들.** CodeMirror(568KB)와 설정·라이브러리 같은 화면은 이미 `lazy`로 나뉘어 있다. 첫 번들 1MB의 대부분은 시작할 때 바로 필요한 xterm이다.

## 2. RAM — 시험해 볼 것 (효과 ÷ 수고 순)

|---|---|---|---|---|---|
| R1 | **최소화 때 WebView2 메모리 목표를 낮춘다** | `lib.rs:2562` `on_window_event`, 기존 `with_webview` 패턴(`lib.rs:2628`) | 창을 최소화해도 렌더러·GPU 프로세스는 쓰던 메모리를 그대로 쥐고 있다(앞 문서 실측에서 G·H 구간이 내려오지 않았다). ### R1 측정 방법

`cpu-ram-risks` 문서와 같은 `measure.ps1` 방식으로 Private Bytes와 Working Set을 **둘 다** 잰다. LOW는 주로 작업 집합(물리 메모리)을 줄이므로 Private Bytes만 보면 효과가 안 보일 수 있다.

1. 셸 2개 + 에이전트 1개를 띄우고 2분 동안 기준선을 잰다.
2. 최소화하고 2분 잰다. R1 적용 전과 후를 비교한다.
3. 복원 직후 첫 화면이 다시 그려지는 데 걸리는 시간을 눈으로 본다. LOW에서 돌아올 때 히치가 생기는지 확인하는 것이다.

## 권하는 순서

1. **R1** — 작고, 기존 패턴(`with_webview`)과 의존성 안에서 끝난다. 효과는 측정해 봐야 안다.
2. **R3** — 숫자만 정하면 한 줄이다. (반영됨, 아래)
3. **R2** — 브라우저 패널을 자주 쓰는 경우에만 한다. 먼저 `browser_close` 대안부터 본다.
4. CPU 쪽은 더 하지 않는다. 남은 항목(C2 FTS 넣었다 지우기, C6 MutationObserver)은 실측에서 비용이 없거나, 이미 rAF와 `touchesCover`로 걸러져 있다.

## 반영 (2026-10-17)

- **R3:** `TerminalPane.tsx`의 `SCROLLBACK_LIVE`를 5000에서 3000으로 내렸다. 120열 기준으로 보이는 페인 하나가 쥐는 링버퍼가 최대 약 7MB에서 약 4MB로 줄고, 페인 8개면 약 23MB가 준다. 내려간 지 60초가 지난 페인의 1000줄(`SCROLLBACK_PARKED`)은 그대로다.
  - 대가가 있다. 페인 안에서 위로 스크롤하거나 Ctrl+F로 찾을 수 있는 범위가 3,000줄로 준다. 디스크 스크롤백은 세션당 1,000줄이라 그 사이 2,000줄을 보충해 주지 못한다. 원시 출력은 세션 로그 파일에 남는다.
  - 숫자를 적은 주석과 문서를 같이 고쳤다. `TerminalPane.tsx` 주석 3곳, `technical-guide.md` 2곳, `eqmux-feature-spec.md` 1곳이다.
  - 검증: `tsc --noEmit` 통과. 앱 실측은 하지 않았다. 확인하려면 출력을 3,000줄 넘게 낸 페인을 맨 위까지 올려 보고, 그때 렌더러 메모리를 이전 빌드와 비교한다.
