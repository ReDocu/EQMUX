결론 먼저

세 줄 요약
Shell
Tauri 2 + Rust
Terax가 터미널·에디터·git·프리뷰·AI를 전부 넣고 7~8MB를 달성했다. Electron으로 같은 기능을 만들면 설치 용량과 상주 메모리가 한 자릿수 배 커진다. AgentCommender(Electron)의 기능 셋을 그대로 옮겨도 이득이 크다.
Core
헤드리스 VT · 데몬 소유
PTY와 터미널 상태를 Rust 데몬이 소유하고, 웹뷰는 보이는 페인만 그린다. 멀티 에이전트 MUX에서 N개 페인이 동시에 쏟아내는 출력을 감당하는 유일한 구조다.
Render
xterm.js WebGL · 가시 페인 한정
WebGL 컨텍스트는 브라우저당 상한(대략 16개)이 있어 페인 수에 비례해 늘릴 수 없다. 가시 페인만 WebGL, 나머지는 스냅샷 이미지로 대체한다.
이 문서가 답하는 질문 "멀티 에이전트 MUX를 만들 때, 5개 레퍼런스 중 무엇을 가져오고 무엇을 버릴 것인가." §2 매트릭스의 마지막 열이 EQMUX 우선순위(P0/P1/P2)이고, §4가 그것을 구현할 스택이다.

비교 대상

각 제품이 증명한 것

Ghostty

터미널 에뮬레이터 · Zig · MIT

네이티브 성능의 상한선. GPU 가속 + 터미널별 읽기/쓰기/렌더 전용 스레드 + 파서 SIMD. AI 기능은 없다 — 순수 터미널이 어디까지 빨라지는지의 기준선.

배울 것
스레드 분리 · OSC 확장 · libghostty식 코어 분리
버릴 것

Orca

멀티 에이전트 IDE · 워크트리 기반

기능 최대주의. 30+ 에이전트 통합, 오케스트레이션(Run/Task/Gate), 데몬 PTY 소유, 원격·모바일까지. 기능 편의성 축의 사실상 상한.

배울 것
데몬 PTY 소유 · 상태 인디케이터 · 오케스트레이션 프로토콜
버릴 것
초기 스코프엔 과대 (워크트리·모바일·클라우드VM)

bbarit-agent-oss

CLI 에이전트 · Rust 단일 바이너리

런타임 의존성 0의 정적 바이너리. 자율 툴 루프, 295 페르소나, 크로스 세션 메모리, --orchestrate 병렬 서브에이전트.

배울 것
메모리/위키 파일 규약 · NDJSON 이벤트 스트림 · 툴 허용목록
버릴 것
GUI 없음 (TUI 전용)

Terax

AI 워크스페이스 · Tauri 2 + React 19

7~8MB에 전부 담은 증거. portable-pty + xterm.js WebGL, CodeMirror 6, OSC 133/777 에이전트 감지, 키체인 키 저장, 시크릿 deny-list.

배울 것
Tauri 2 구조 · OSC 777 상태 규약 · 승인 게이트 · deny-list
버릴 것
탭마다 xterm 영속 마운트(페인 수 확장에 불리)

AgentCommender

팀·임무 관제 MUX · Electron

EQMUX의 직계 선행 제품. 팀=탭 / 세션=페인, 임무(MISSION.md) 배정, 팀 편성 관계도, acmux CLI 제어, git·포트·브라우저 패널.

배울 것
도메인 모델 전체(팀·임무·배정) · CLI 프로토콜 · Job Object
버릴 것
Electron 런타임 · Windows 전용 가정

축별 심층 비교

무엇을 가져오고 무엇을 버릴 것인가

3.1 터미널 코어 — 페인 수가 늘어날 때 무너지는 지점

설계 선택채택 제품 N개 페인 동시 스트리밍 시
전용 스레드 분리Ghostty (읽기/쓰기/렌더) 터미널당 스레드 3개. 페인 8개면 스레드 24개 — 네이티브라 감당되지만 웹뷰 구조에선 불가. Rust 데몬에서 async 태스크로 축소 구현이 현실적.
탭마다 xterm 영속 마운트Terax · AgentCommender 숨겨진 탭도 파싱·버퍼 유지 비용을 계속 낸다. 세션 4개면 활성 탭은 무해하지만, EQMUX는 워크스페이스 탭을 최대 10개까지 열어 총 40세션이 될 수 있다. 비활성 탭의 36세션이 여기에 해당한다.
데몬이 PTY 소유Orca 앱을 닫아도 에이전트가 계속 돈다. 앱이 죽어도 세션이 살아남는 건 장시간 도는 에이전트에겐 기능이 아니라 요구사항. EQMUX 필수 채택.
Job Object 프로세스 트리 정리Terax · AgentCommender Windows에서 에이전트가 띄운 손자 프로세스(node·python·docker)가 고아로 남는 문제를 원천 차단. 둘 다 독립적으로 같은 결론에 도달했다는 게 근거.
확인이 필요한 제약 — WebGL 컨텍스트 상한 Chromium 계열은 살아있는 WebGL 컨텍스트 수에 상한(대략 16개)이 있고, 초과하면 오래된 컨텍스트부터 강제 소실된다. 페인마다 xterm WebGL 렌더러를 붙이는 구조는 페인 8~16개 구간에서 "배경 터미널이 검게 변하는" 버그로 나타난다. 가시 페인만 WebGL, 비가시 페인은 정지 스냅샷으로 설계하고, 실제 상한은 타깃 WebView2에서 실측할 것.

3.2 에이전트 레이어 — 상태를 어떻게 알아내는가

감지 방식출처 정확도 / 비용
출력 시각 휴리스틱AgentCommender 마지막 출력 <3초=활성, <60초=진행. 구현이 가장 싸지만 "입력 대기"와 "생각 중"을 구분 못 한다 — 멀티 에이전트에선 이 구분이 전부다.
OSC 133 + OSC 777Terax 셸 통합 마커로 무장 후 명시적 시퀀스에서만 상태 전이. 셸·tmux 무관, TUI 리페인트 오탐 없음, 에이전트 미실행 시 비용 0. 최적해.
에이전트 훅Terax · Orca Claude Code 훅 3종(UserPromptSubmit/Notification/Stop)이 OSC를 되돌려준다. OSC를 못 뱉는 에이전트의 보강 수단이지 대체재가 아니다.
NDJSON 이벤트 스트림bbarit 에이전트가 --mode json을 지원하면 가장 정확. 지원 에이전트가 소수라 1급 경로로 삼되 폴백 필요.
EQMUX 채택 3계층 폴백 — ① NDJSON 스트림(지원 시) → ② OSC 777 훅 → ③ OSC 133 + 출력 휴리스틱. 감지 로직은 전부 Rust 데몬의 PTY 리더 안에 두어 프런트엔드가 관여하지 않게 한다.

3.3 도메인 모델 — EQMUX만의 자산

5개 중 팀 · 직책 · 관계 · 임무 배정 모델을 가진 것은 AgentCommender뿐이다. Orca는 워크트리를, bbarit은 페르소나를 단위로 삼는다. 세 모델의 성격이 다르다.

단위제품강점약점
워크트리Orca코드 충돌 원천 차단, git 네이티브 디스크 사용량, 의존성 재설치, 팀 개념 없음
페르소나bbarit역할별 프롬프트 자산 295개, 읽기전용 모드 에이전트 간 관계·보고 체계 없음
팀 + 임무AgentCommender 보고 관계·직책·일괄 명령, MISSION.md가 파일로 남는 원본 코드 격리 없음(같은 폴더 동시 편집 위험)
합성 제안 팀·임무 모델(AgentCommender)을 코어로 두고, 임무 단위에 선택적 워크트리 격리(Orca)를 옵션으로 얹는다. 페르소나는 팀원의 직책 필드에 프롬프트 프리셋으로 매핑한다. 파일 원본 규약(MISSION.md · TEAM.md · CLAUDE.md 블록)은 그대로 유지 — 에이전트가 읽을 수 있는 유일한 공용 상태이기 때문.
04

권장 기술 스택

선택 · 대안 · 근거 · 리스크
레이어권장 대안근거 / 리스크
앱 셸 Tauri 2 (Rust)Electron · Wails Terax가 동급 기능으로 7~8MB 달성. WebView2는 Win11에 기본 탑재, 오프라인 번들도 가능. 리스크: Linux WebKitGTK 렌더 편차 — 1차는 Windows 타깃이라 유예 가능.
PTY portable-pty (wezterm)conpty-rs · node-pty Terax 채택, ConPTY/Unix 추상화 완비. node-pty는 Node 런타임을 끌고 오므로 탈락.
VT 파서 vte (alacritty) 또는 termwiz프런트 xterm.js 단독 핵심 결정. Rust에 헤드리스 터미널 상태를 두면 비가시 페인의 렌더러 비용이 0이 되고, 스크롤백·검색·OSC 감지를 전부 백엔드에서 처리할 수 있다.
터미널 렌더 xterm.js + WebGL (가시 페인만)자체 canvas 렌더러 직접 구현은 리가처·이모지·IME·그래핌 클러스터에서 1년을 잃는다. WebGL 컨텍스트 상한을 페인 수 상한으로 삼고 초과분은 스냅샷 처리.
프런트 SolidJS + ViteReact 19 (Terax) · Svelte 5 VDOM 없는 세밀 반응성. 8개 페인의 상태 점·타이머·바이트 카운터가 초당 수십 번 갱신되는 대시보드에서 리렌더 비용 차이가 그대로 드러난다. 리스크: 생태계가 React보다 얇다 — 팀 숙련도 우선이면 React도 합리적.
에디터 CodeMirror 6Monaco Monaco는 수 MB 단위라 "7MB 앱" 목표와 양립 불가. Terax도 CM6.
상태 저장 SQLite(rusqlite) + JSON 설정전부 JSON 스크롤백·세션 로그·이벤트는 append 중심 + 검색 필요 → SQLite. 사용자 설정만 사람이 읽는 JSON으로. AgentCommender의 state.json 전체 재작성 방식은 세션이 늘수록 불리.
git git CLI + gix(읽기 경로)libgit2 · 전부 CLI 자격증명 헬퍼·훅·서브모듈 호환은 CLI가 정답. 커밋 그래프·status 같은 고빈도 읽기만 gix로 가속. GIT_OPTIONAL_LOCKS=0 필수(AgentCommender 선례).
코드 검색 ignore + grep 크레이트ripgrep 바이너리 동봉 ripgrep의 엔진을 라이브러리로 링크 — 외부 바이너리 없이 동일 성능. Terax가 fs_grep으로 같은 선택.
브라우저 패널 Tauri 2 자식 웹뷰iframe · 외부 브라우저 iframe은 X-Frame-Options에 막힌다(AgentCommender가 WebContentsView로 우회한 이유). 리스크: Tauri 멀티 웹뷰는 unstable 플래그 — 채택 전 타깃 버전에서 검증 필요.
IPC Tauri Channel + 바이너리 프레임로컬 WebSocket PTY 출력을 JSON 문자열/base64로 보내면 인코딩 비용이 렌더 비용을 넘어선다. Uint8Array 그대로 보낼 것.
외부 제어 named pipe / UDS + NDJSONHTTP 로컬 서버 acmux 프로토콜을 그대로 계승. 포트를 열지 않아 방화벽·보안 경고가 없다.
빌드 opt-level="z" · LTO · strip기본 release codegen-units=1, panic="abort" 병행. UPX 압축은 비권장 — 백신 오탐을 부른다.
세 기준별 최대 기여 항목
  • 성능 — 헤드리스 VT(비가시 페인 비용 0) > 프레임 코얼레싱 > 바이너리 IPC
  • 메모리·용량 — Tauri(런타임 미포함) > 스크롤백 디스크 스필 > CM6 > Solid
  • 기능 편의성 — 데몬 PTY 소유(세션 생존) > OSC 상태 감지 > CLI 제어 > 자식 웹뷰
05

아키텍처

3 프로세스 · 데몬이 진실의 원천

데이터 흐름 3가지

  • 가시 페인 — PTY 바이트 → 데몬 VT 갱신 → 8~16ms 단위로 묶어 Uint8Array 전송 → xterm.js WebGL 렌더
  • 비가시 페인 — PTY 바이트 → 데몬 VT 갱신 후 종료. 전송 없음. 페인이 보이는 순간 화면 스냅샷 1회만 전송
  • 상태 이벤트 — OSC 감지 → 상태 머신 → 대시보드·알림·탭 배지에 소량 JSON 이벤트
06

성능 · 메모리 예산

목표치 — 측정으로 검증할 것
아래 숫자는 측정값이 아니라 설계 예산이다 5개 문서에서 확인된 사실은 Terax 번들 7~8MB와 AgentCommender 스크롤백 10,000줄 / 팀당 8세션뿐이다. 나머지는 구조에서 역산한 목표치이므로, M1 프로토타입에서 실측해 교정할 것.
항목목표 산출 근거 / 달성 수단
설치 용량≤ 15 MB Terax 7~8MB가 실증한 상한. git·검색 엔진을 링크하면 증가하므로 15MB를 상한으로 잡는다. WebView2는 시스템 공유(Win11 기본 탑재).
빈 창 상주 메모리≤ 120 MB WebView2 프로세스군 + Rust 데몬. Electron 대비 절감분이 여기서 나온다.
세션당 메모리 (활성 탭)≤ 32 MB xterm.js 셀 버퍼는 셀당 uint32 3개(≈12B). 200열 × 5,000줄 ≈ 12MB + WebGL 텍스처 아틀라스. 활성 탭은 4세션 전부 가시이므로 인메모리 스크롤백을 5,000줄까지 올릴 여유가 생겼다.
세션당 메모리 (비활성 탭)≤ 4 MB Rust VT 상태만 유지. 렌더러 객체·WebGL 컨텍스트·JS 힙 모두 0. 이 항목이 헤드리스 VT를 채택하는 이유 전부이며, 세션 상한이 4로 내려간 뒤 절약 지점이 "숨은 페인"에서 "비활성 워크스페이스 탭"으로 이동했다.
최대 규모 총합≤ 400 MB 워크스페이스 10개 × 세션 4개 = 40세션. 120 + (활성 4 × 32) + (비활성 36 × 4) ≈ 392MB. 에이전트 CLI 프로세스 자체는 별도이며, 실질 제약은 앱이 아니라 그쪽이다.
스크롤백 보존량무제한 (디스크) 인메모리 링버퍼 5,000줄 + SQLite 스필(워크스페이스별 DB). 위로 스크롤할 때만 페이징. AgentCommender의 10,000줄 × 8페인을 전부 램에 두는 방식과 대비.
PTY → 화면 지연≤ 32 ms 코얼레싱 프레임 16ms + 렌더 1프레임. 사람이 인지하는 하한 근처.
폭주 출력 처리드롭 허용 가시 페인도 프레임당 바이트 상한을 두고 초과분은 VT에만 반영하고 전송은 생략. yes·대형 빌드 로그에서 UI가 멈추지 않는 조건.
콜드 스타트≤ 400 ms 데몬 상주 시 GUI는 뷰 복원만. 세션 복원은 스냅샷 1회 전송으로 끝난다.
07

안티패턴

레퍼런스에서 관찰된 함정
  • 모든 페인에 살아있는 WebGL 렌더러를 붙이지 말 것 컨텍스트 상한을 넘기면 배경 페인이 소실된다. 가시 페인 수를 상한으로 설계하고 나머지는 스냅샷으로 대체.
  • PTY 바이트를 JSON 문자열이나 base64로 IPC 하지 말 것 인코딩 비용이 렌더 비용을 넘는다. 바이너리 채널 + 프레임 코얼레싱이 기본값이어야 한다.
  • 비가시 페인에 출력을 계속 전송하지 말 것 8개 에이전트가 동시에 빌드 로그를 뿜으면 화면에 없는 7개가 프레임 예산을 다 먹는다.
  • 대용량 스크롤백을 렌더러 힙에 두지 말 것 10,000줄 × 8페인은 곧 수백 MB다. 인메모리는 짧게, 나머지는 디스크에.
  • 상태 파일 전체를 매번 다시 쓰지 말 것 세션·이벤트가 누적되면 디바운스로도 못 막는다. append 구조(SQLite)로 분리.
  • 에이전트 상태를 출력 시각만으로 판정하지 말 것 "입력 대기"와 "생각 중"이 구분되지 않으면 관제 대시보드의 존재 이유가 사라진다.
  • 프런트엔드에서 시크릿 접근을 막지 말 것 deny-list는 경로 정규화 이후 Rust에서 강제해야 우회 불가능하다 — Terax의 설계.
  • Monaco·무거운 UI 킷·런타임 CSS-in-JS를 넣지 말 것 "작은 앱" 목표는 의존성 하나로 무너진다. CM6 + 컴파일타임 CSS.
  • 1차 출시에 워크트리·모바일·클라우드 VM을 넣지 말 것 Orca의 표면적은 수년치다. P0 열에 없는 것은 넣지 않는다.
08

도입 순서

각 단계에서 검증할 가설
  1. 데몬 + PTY + 헤드리스 VT 스파이크 GUI 없이 8개 PTY를 붙여 폭주 출력 시 CPU·메모리를 실측한다. 검증 가설: 비가시 페인 4MB / 총 400MB 예산이 성립하는가.
  2. Tauri 셸 + xterm.js 브리지 바이너리 채널로 코얼레싱 프레임 전송, 가시/비가시 전환과 스냅샷 복원. 검증 가설: WebGL 컨텍스트 상한과 전환 지연이 수용 가능한가.
  3. 탭·스플릿 · 그리드 · 세션 영속 AgentCommender 레이아웃 모델(분할 트리 + 4×2 그리드 + 8세션)을 이식. 앱 재시작 후 세션 생존과 스크롤백 페이징까지.
  4. 에이전트 실행 · OSC 상태 머신 · 알림 Claude Code·Codex·Gemini 실행, 3계층 상태 폴백, Terax식 3단 알림 라우팅. 여기까지가 "멀티 에이전트 MUX"의 최소 정의.
  5. 팀 · 임무 · 관제 대시보드 team.json·TEAM.md·MISSION.md 규약과 배정 로직, 관계도, 일괄 명령. EQMUX의 차별점이 처음 드러나는 단계.
  6. CLI 제어 · git 패널 · 브라우저 패널 acmux 프로토콜 계승, gix 커밋 그래프, 자식 웹뷰. 여기서부터 P1 — 앞 단계가 안정된 뒤에 착수.
